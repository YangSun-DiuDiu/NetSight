# 工作流状态统一与「历史已办」为空问题分析与改造方案

- 版本：v1.1（已实施并上线测试环境）
- 日期：2026-11-06
- 范围：NetSight 工作流（warm-flow 1.8.9）+ 统一待办页 + 审批单
- 状态：**代码改造、存量回填、后端/前端部署、接口与页面实测均已完成**（测试环境 115.159.194.149）
- 结论依据：源码走查 + 线上库（115.159.194.149 / netsight）实测 + warm-flow-core-1.8.9.jar 反编译 + 实施后页面实测

## 0. 结论摘要

| # | 现象 | 根因（一句话） | 性质 |
|---|------|----------------|------|
| 1 | 审批待办「状态」列显示 `1` | 引擎返回**数字码** `"1"`，前端字典 `FLOW_STATUS_TEXT` 的键却是**英文枚举名** `APPROVAL`，取不到就回退渲染原始值 | 展示层字典键不匹配，数据本身正确 |
| 2 | sunyang21 审批过的单子查不到 | `flow_his_task.tenant_id` **全部为 NULL**，`myDone` 的 SQL 却硬过滤 `h.tenant_id = '7'` | 写入漏回填 + 查询强依赖该列 |

两个问题都不需要改 warm-flow 引擎：一个是**映射边界缺失**，一个是**运行时表租户列漏写**。

> 同一根因还有第三个症状：`flow_user.tenant_id` 为空会让「待办」也消失（线上已存在 1 条这样的待办，见 2.6）。修复范围必须覆盖 `flow_task / flow_user / flow_his_task` 三张运行时表。

**能否纳入统一状态管理：可以，而且应该。** 但不建议直接把引擎 0~13 的数字码铺到页面上——引擎码是「引擎内部语言」，必须在一个边界上翻译成业务状态，页面只认业务状态。

**附带发现（同一批改动应一并处理）**

1. 「历史已办」若不排除 `start` 节点，修好租户过滤后每个人都会看到自己**发起**的记录，与「我审批过的」语义不符（实测 sunyang21 名下 17 条中，9 条是发起、8 条是审批）。
2. 「我的结果」列按 `skipType` 判断通过/驳回，但**驳回走 `terminationByInsId`，落库 `skip_type` 仍是 `PASS`**，会把驳回显示成「通过」（实测 5 条驳回全是 `skip_type=PASS`、`flow_status=4`）。
3. `approval_bill.flow_name` 线上全部为 NULL，历史列表「流程」列为空。

## 1. 问题一：页面为什么显示 `1`

### 1.1 落点

`netsight-ui/src/views/todo/index.vue`

- L54-60：类型筛选，`workflow` = 审批待办，`done` = 历史已办
- L193-196：字典定义

```js
const FLOW_STATUS_TEXT = {
  TOBESUBMIT: '待提交', APPROVAL: '审批中', PASS: '已通过', REJECT: '已驳回',
  TERMINATE: '已终止', CANCEL: '已撤销', RETRIEVE: '已撤回', FINISHED: '已完成'
}
```

- L249-250：取值

```js
statusText: FLOW_STATUS_TEXT[t.flowStatus] || t.flowStatus || '审批中',
statusTag: t.flowStatus === 'APPROVAL' ? 'primary' : 'warning',
```

字典的**键是英文枚举名**，而 `t.flowStatus` 实际是**数字字符串** `"1"`。`FLOW_STATUS_TEXT["1"]` 为 `undefined`，于是 `|| t.flowStatus` 生效，页面显示 `1`；同时 `t.flowStatus === 'APPROVAL'` 永远为 false，标签颜色永远落在 `warning`。

### 1.2 三层证据链

**第一层：引擎写的是数字码**

`flow_task` 当前待办行实测：`flow_status = '1'`。

反编译 `warm-flow-core-1.8.9.jar` → `org.dromara.warm.flow.core.enums.FlowStatus`，完整取值：

| key | 枚举 | 含义 |
|-----|------|------|
| 0 | TOBESUBMIT | 待提交 |
| 1 | APPROVAL | 审批中 |
| 2 | PASS | 审批通过 |
| 3 | AUTO_PASS | 自动完成 |
| 4 | TERMINATE | 终止 |
| 5 | NULLIFY | 作废 |
| 6 | CANCEL | 撤销 |
| 7 | RETRIEVE | 取回 |
| 8 | FINISHED | 已完成 |
| 9 | REJECT | 驳回 |
| 10 | INVALID | 失效 |
| 11 | TASK_BACK | 回退 |
| 12 | RE_START | 重新开始 |
| 13 | PENDING | 暂存 |

即：`1` = 审批中，值本身没错，错在没人翻译。

**第二层：后端原样透传**

`WorkflowService.java`

- L548-556 `buildTodoItem()`：`item.put("flowStatus", task.getFlowStatus())` —— 直接把引擎数字码放进响应
- L407-415 `billDetail()`：`hisTaskService.list(...)` 原样返回 `HisTask` 实体，未做 DTO 映射
- L387-399 `myDone()`：`h.flow_status AS flowStatus` 原样带出

后端没有任何「引擎码 → 业务状态」的转换层。

**第三层：前端各自维护字典**

- `todo/index.vue`：`FLOW_STATUS_TEXT`（英文键）
- `workflow/started/index.vue`：`STATUS_MAP`（业务字符串键），列表正常；但详情时间线 L104 写的是

```vue
<span class="his-op">{{ h.handlerType || h.flowStatus || '' }}</span>
```

`handlerType` 为空时直接把 `2` / `4` 显示出来，这是第二处数字泄漏。

- `workflow/definition/index.vue`：`isPublish`（1/9/0）、`activityStatus`（1/0）又是另一套数字直出，属于「流程定义域」，不在本次审批状态范围内，但可复用同一套组件。

### 1.3 结论

问题一不是「1 这个值错了」，而是系统里存在**三层状态各自为政**：

```
引擎数字码（flow_instance / flow_task / flow_his_task）
        ↓ 无人翻译
审批单业务字符串（approval_bill.approval_status：processing / approved / rejected / canceled）
        ↓ 各页面自己写 Map
前端展示（有的对、有的显示数字、有的显示英文）
```

## 2. 问题二：历史审批记录为什么是空的

### 2.1 入口确认

「历史审批记录」不是独立菜单页，而是**待办中心** `views/todo/index.vue` 的「历史已办」标签（L59），点击后调用 `GET /workflow/mine/done`（`api/workflow/workflow.js` L57），后端 `WorkflowService.myDone()`。

### 2.2 根因

`myDone()`（L362-402）的统计 SQL：

```sql
SELECT COUNT(*) FROM flow_his_task h
WHERE h.approver = ? AND h.tenant_id = ? AND h.del_flag = '0'
```

明细 SQL 同样带 `h.tenant_id = ?`，再 `LEFT JOIN approval_bill b ON b.process_instance_id = h.instance_id`。

线上库实测：

- `flow_his_task` 共 **69 条**，**`tenant_id` 全部为 NULL**（无一例外）
- `del_flag` 全部为 `'0'`
- approver 分布：1→39、5→17、19→8、18→3、17→1、16→1

因此 `h.tenant_id = '7'` 命中 **0 行**。

### 2.3 对照实验（同一账号、同一批数据）

| 查询 | 条件 | 结果 |
|------|------|------|
| A | 现有 SQL：`approver='5' AND tenant_id='7'` | **0 条** |
| B | 去掉 tenant_id 过滤 | **17 条** |
| C | 改按 `approval_bill.tenant_id=7` 过滤 | **17 条** |
| D | C + 排除 `node_type=0`（start 节点） | **8 条** |

A=0 与 B=17 的差异，就是「单据确实审批了、历史行也确实写了，丢的是查询过滤条件」。

按新 SQL（`b.tenant_id=7` + 排除 start）实测返回 **8 条**，其中：

- 7 条为 2026-11-05/06 的备件出库审批（`OUT202611051604313088` ~ `OUT202611061009382999`）
- 1 条为 2026-10-15 的租户 7 E2E 测试单（`WF-T7-E2E-520049`）

审批动作本身有据可查：`approval_bill` id 32~38 全部为 `tenant_id=7 / biz_type=out_stock / flow_code=spare_out_stock / approval_status=approved / apply_user_id=5（孙扬）`，对应 `flow_his_task` 有 `approver='5'、node_code='approve'、skip_type='PASS'、flow_status='2'` 的记录，时间集中在 2026-11-05 16:04~16:30 与 2026-11-06 10:09。

### 2.4 为什么只有 `flow_his_task` 没租户

`start()` 的租户回填（L144-150）只覆盖三张表：

```java
jdbcTemplate.update("UPDATE flow_instance SET tenant_id = ? WHERE id = ?", tenant, instance.getId());
jdbcTemplate.update("UPDATE flow_task SET tenant_id = ? WHERE instance_id = ?", tenant, instance.getId());
jdbcTemplate.update("UPDATE flow_user SET tenant_id = ? WHERE associated IN (SELECT id FROM flow_task WHERE instance_id = ?)", tenant, instance.getId());
```

**没有 `flow_his_task`**。

而 `flow_his_task` 不是在 `start()` 时写入的——它由审批时的 `taskService.skip()` / `terminationByInsId()` 写入，`approve()` 与 `revoke()` 里没有任何补写租户的代码。`WarmFlowSaveInterceptor` 只回填 `flow_definition`，与运行时表无关。

对照证据：`flow_task` 的行 `tenant_id='7'` 正常（被 `start()` 回填过），`flow_his_task` 全 NULL——差异恰好对应「漏了第四张表」。

### 2.5 两个连带缺陷

**A. `start` 节点会混进「我审批过的」**

`flow_his_task` 里 `node_code='start'、node_type=0` 的 38 条记录，`approver` 记的是**发起人**。sunyang21 名下 17 条中有 **9 条是发起节点、只有 8 条是真实审批**。租户条件修好后，他会在「我审批过的」里看到自己「发起」的记录，多条单子还会重复出现两次（start + approve）。

**B. 驳回被显示成「通过」**

`todo/index.vue` L73-78：

```vue
<el-tag v-if="row.skipType === 'PASS'" type="success">通过</el-tag>
<el-tag v-else-if="row.skipType === 'REJECT'" type="danger">驳回</el-tag>
```

但驳回走的是 `taskService.terminationByInsId()`，落库 `skip_type` 仍是 `PASS`、`flow_status='4'`。实测 `flow_his_task` 组合分布：

- `start / 0 / PASS / 2`：38 条
- `approve / 1 / PASS / 2`：26 条
- `approve / 1 / PASS / 4`：5 条 ← **这 5 条就是被显示成「通过」的驳回单**

真正能区分的是 `flow_status` + 单据终态，不是 `skipType`。

### 2.6 同一根因的第三个症状：待办也会“消失”

线上还存在一条 `flow_task` 待办（`id=2109968678875287555`，节点「租户管理员审批」，`create_time=2026-10-13 19:25:09`）的 `tenant_id` 为 NULL；其关联 `flow_user` 行的 `tenant_id` 同样为 NULL，而对应审批单 `approval_bill.id=3` 的 `tenant_id=1`。

`myTodo()`（L319-323）的查询条件是：

```java
.eq(FlowUser::getTenantId, tenantId)
.in(FlowUser::getProcessedBy, identities)
```

`flow_user.tenant_id` 为 NULL → 该待办对租户 1 的审批人**不可见**。

也就是说，租户列漏填不只让“历史”查不到，也会让“待办”丢单。修复必须同时覆盖 `flow_task` / `flow_user` / `flow_his_task`，不能只补历史表。

## 3. 统一状态模型设计

### 3.1 四条原则

1. **单一事实来源**：业务状态的文案/颜色只在后端定义一次，前端不再各写 Map。
2. **边界翻译**：引擎数字码不出口到 API；在 Service 出口处翻译成业务状态。
3. **业务态优先于引擎态**：引擎 `4=终止` 同时被「驳回」和「撤销」复用，不能单凭引擎码判断业务结果，必须结合 `approval_bill.approval_status`。
4. **向后兼容**：数据库列不改类型、不清洗历史值；新增字段/映射是纯增量。

### 3.2 建议的三层模型

```
① 引擎态  flow_status 0~13        —— 只存引擎表，不出 API
        ↓ WarmFlowStatusMapper
② 业务态  processing / approved / rejected / canceled
        ↓ ApprovalStatusResolver（结合 bill 状态消歧）
③ 展示态  { code, text, tag }      —— API 唯一出口，前端直接渲染
```

### 3.3 业务状态枚举（后端唯一来源）

新增 `com.netsight.modules.workflow.constant.WorkflowStatus`（参照现有 `WorkOrderStatus` 的 code+text 写法）：

```java
public enum WorkflowStatus {
    PROCESSING("processing", "审批中", "warning"),
    APPROVED  ("approved",   "已通过", "success"),
    REJECTED  ("rejected",   "已驳回", "danger"),
    CANCELED  ("canceled",   "已撤销", "info");

    private final String code;
    private final String text;
    private final String tag;
    // getter / of(code) / textOf(code) / tagOf(code)
}
```

沿用 `approval_bill.approval_status` 与 `spare_out_request.approval_status` 现有的四个字符串值，**不迁移存量数据**。

### 3.4 引擎码 → 业务态映射

`WarmFlowStatusMapper`（新增）：

| 引擎 key | 枚举 | 业务态 | 说明 |
|---------|------|--------|------|
| 0 | TOBESUBMIT | processing | 待提交（本系统 start 即提交，实际少见） |
| 1 | APPROVAL | processing | 审批中 |
| 2 | PASS | approved | 审批通过 |
| 3 | AUTO_PASS | approved | 自动完成 |
| 4 | TERMINATE | **需消歧** | 驳回与撤销都用它 |
| 5 | NULLIFY | canceled | 作废 |
| 6 | CANCEL | canceled | 撤销 |
| 7 | RETRIEVE | canceled | 取回 |
| 8 | FINISHED | approved | 已完成 |
| 9 | REJECT | rejected | 驳回 |
| 10 | INVALID | canceled | 失效 |
| 11 | TASK_BACK | processing | 回退中 |
| 12 | RE_START | processing | 重新开始 |
| 13 | PENDING | processing | 暂存 |

`4` 的消歧规则：

```
flow_status = 4 且 bill.approval_status = rejected  → rejected（驳回）
flow_status = 4 且 bill.approval_status = canceled  → canceled（撤销）
flow_status = 4 且无单据                       → canceled（兜底）
```

之所以必须消歧：`approve(pass=false)` 与 `revoke()` 都调用 `taskService.terminationByInsId()`，引擎侧落的是同一个 `4`。

### 3.5 节点动作（历史轨迹用）

历史轨迹里的「我的结果」不是单据状态，而是**节点动作**，单独用一个枚举：

| 条件 | 动作 | 文案 |
|------|------|------|
| node_type = 0 | START | 发起 |
| flow_status ∈ (2,3,8) 且 node_type ≠ 0 | PASS | 通过 |
| flow_status = 4 且 bill = rejected | REJECT | 驳回 |
| flow_status = 4 且 bill = canceled | CANCEL | 撤销 |
| flow_status ∈ (6,7) | RETRIEVE | 撤回 |
| 其他 | PENDING | 处理中 |

### 3.6 API 输出契约

所有与审批状态相关的接口，统一多返回三个字段（保留原字段以兼容旧页面）：

```json
{
  "statusCode": "processing",
  "statusText": "审批中",
  "statusTag": "warning"
}
```

历史轨迹节点：

```json
{
  "actionCode": "reject",
  "actionText": "驳回",
  "actionTag": "danger",
  "statusCode": "rejected",
  "statusText": "已驳回",
  "statusTag": "danger"
}
```

前端**不再自己算文案和颜色**，`statusText` 缺失时才回退本地兜底字典。

### 3.7 前端统一组件

新增 `netsight-ui/src/components/StatusTag/index.vue`：

```vue
<status-tag :code="row.statusCode" :text="row.statusText" :tag="row.statusTag" domain="workflow" />
```

- 传了 `text/tag` 就直接渲染（后端为准）
- 未传则按 `domain + code` 查本地兜底字典（离线/旧接口可用）
- 统一 `size="mini"`，与 2026-10-02 定下的状态列规范一致

首批接入：

1. `views/todo/index.vue`：审批待办状态列、历史已办「我的结果」「单据当前状态」、审批弹窗轨迹
2. `views/workflow/started/index.vue`：详情时间线（替换 `h.flowStatus`）
3. `views/workflow/definition/index.vue`：发布状态 / 激活状态（同组件，`domain="definition"`）

### 3.8 三个可选方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A. 后端枚举 + 前端组件 | 本次推荐 | 编译期安全、可单测、无运维成本、引擎码不外泄 | 新增状态要发版 | **推荐** |
| B. 全部走若依字典 `sys_dict_data` | 现状已有 `dict-tag` 基建 | 运营可改文案/颜色 | 仍需后端把引擎码转成业务码；字典无法表达 4 的消歧逻辑；要初始化多套字典 | 可作为二期增强，不是一期 |
| C. 只在各页面补 Map | 最小改动 | 快 | 仍然是多层各自为政，新增状态必漏，正是当前问题的成因 | 不采纳 |

**建议 A，并保留 B 的口子**：`StatusTag` 组件优先用后端 text/tag，后续若接字典只替换兜底来源，页面无需再改。

## 4. 问题二修复方案：写时补 + 存量回填 + 读时兜底

三层同时做，缺一层都会复发。

### 4.1 写入侧：每次引擎状态变更后补租户

在 `WorkflowService` 新增：

```java
private void syncRuntimeTenant(Long instanceId) {
    String tenant = String.valueOf(SecurityUtils.getTenantId());
    jdbcTemplate.update("UPDATE flow_instance SET tenant_id = ? WHERE id = ? AND tenant_id IS NULL", tenant, instanceId);
    jdbcTemplate.update("UPDATE flow_task SET tenant_id = ? WHERE instance_id = ? AND tenant_id IS NULL", tenant, instanceId);
    jdbcTemplate.update("UPDATE flow_user SET tenant_id = ? WHERE associated IN " +
            "(SELECT id FROM flow_task WHERE instance_id = ?) AND tenant_id IS NULL", tenant, instanceId);
    jdbcTemplate.update("UPDATE flow_his_task SET tenant_id = ? WHERE instance_id = ? AND tenant_id IS NULL", tenant, instanceId);
}
```

调用点：

- `start()`：把现有 L147-150 的三条 UPDATE 收敛为 `syncRuntimeTenant(instance.getId())`（顺手补上第四张）
- `approve()`：`skip` / `terminationByInsId` 之后调用
- `revoke()`：`terminationByInsId` 之后调用

> 为什么必须放在 `approve`：`skip` 会创建下一节点的 `flow_task` / `flow_user`，这些新行同样是引擎直写、`tenant_id` 为 NULL。当前流程只有单审批节点所以没暴露，一旦上多节点，**下一个审批人会在待办里看不到任务**——这是同一个根因的潜伏形态，必须一起修。

### 4.2 查询侧：`myDone` 不再依赖 `flow_his_task.tenant_id`

统计 SQL：

```sql
SELECT COUNT(*)
FROM flow_his_task h
INNER JOIN approval_bill b ON b.process_instance_id = h.instance_id
WHERE h.approver = ?
  AND h.del_flag = '0'
  AND h.node_type <> 0          -- 排除发起节点
  AND b.tenant_id = ?
  AND b.del_flag = '0'
```

明细 SQL 在此基础上：

```sql
SELECT h.id AS hisId, h.instance_id AS instanceId, h.node_name AS nodeName,
       h.node_type AS nodeType, h.skip_type AS skipType, h.flow_status AS rawFlowStatus,
       h.message AS myComment, h.create_time AS approveTime,
       b.id AS billId, b.biz_id AS bizId, b.title AS title, b.flow_name AS flowName,
       b.biz_type AS bizType, b.apply_user_name AS applyUserName,
       b.approval_status AS currentBillStatus
FROM flow_his_task h
INNER JOIN approval_bill b ON b.process_instance_id = h.instance_id
WHERE h.approver = ? AND h.del_flag = '0' AND h.node_type <> 0
  AND b.tenant_id = ? AND b.del_flag = '0'
ORDER BY h.create_time DESC
LIMIT ? OFFSET ?
```

然后用 `ApprovalStatusResolver.resolve(h.rawFlowStatus, b.approval_status)` 在 Java 侧补 `resultCode/resultText/resultTag` 与 `statusCode/statusText/statusTag`。

要点：

- 用 `INNER JOIN` 而不是 `LEFT JOIN`：无单据的引擎裸数据不应出现在业务列表
- 租户过滤改到 `b.tenant_id`：单据表是业务权威，且历史行该列为 NULL
- `node_type <> 0`：保证「我审批过的」只含审批动作
- 不删 `flow_status` 原字段：旧前端仍可用，新前端用映射字段

### 4.3 存量数据回填（一次性，幂等）

先备份：

```sql
CREATE TABLE flow_his_task_bak_20261106 AS SELECT * FROM flow_his_task;
CREATE TABLE flow_task_bak_20261106     AS SELECT * FROM flow_task;
CREATE TABLE flow_user_bak_20261106     AS SELECT * FROM flow_user;

```

回填（按单据租户，全部租户，可重复执行）：

```sql
UPDATE flow_his_task h
JOIN approval_bill b ON b.process_instance_id = h.instance_id
SET h.tenant_id = b.tenant_id
WHERE h.tenant_id IS NULL AND b.tenant_id IS NOT NULL;

UPDATE flow_task t
JOIN approval_bill b ON b.process_instance_id = t.instance_id
SET t.tenant_id = b.tenant_id
WHERE t.tenant_id IS NULL AND b.tenant_id IS NOT NULL;

UPDATE flow_instance i
JOIN approval_bill b ON b.process_instance_id = i.id
SET i.tenant_id = b.tenant_id
WHERE i.tenant_id IS NULL AND b.tenant_id IS NOT NULL;

UPDATE flow_user u
JOIN flow_task t ON u.associated = t.id
JOIN approval_bill b ON b.process_instance_id = t.instance_id
SET u.tenant_id = b.tenant_id
WHERE u.tenant_id IS NULL AND b.tenant_id IS NOT NULL;
```

说明：

- 只填 `tenant_id IS NULL` 的行，不覆盖已有值
- 找不到对应单据的引擎测试数据保持 NULL（本就不该出现在业务列表）
- 建议在低峰执行，单表 69 行，秒级完成
- 回滚：`UPDATE ... JOIN 备份表` 还原，或直接 `TRUNCATE + INSERT SELECT`（表量极小）

### 4.4 为什么读侧仍要留 `bill` 兜底

即便写侧补齐，历史数据、引擎升级、或未来新表仍可能漏填。读侧以 `approval_bill.tenant_id` 为准，可以保证「即使某天引擎又少填一列，列表也不会整页空白」。写侧负责让数据正确，读侧负责让页面不脆。

**列结构错位的排查与最终修法（重要经验）**

切换「历史已办」后表头与表体来自不同列定义，出现「点检」「—」等错位。四轮尝试：

1. 外层 `<template v-if>` 包裹整组列 → 失败
2. 逐列 `v-if` → 仍失败（表头 10 列 / 表体 0 行，表头 0 列 / 表体 8 行）
3. 两套独立 `el-table`（`v-if` / `v-else`）→ 仍失败
4. **两套 `el-table` + 各自不同 `key`（`doneTable` / `todoTable`）→ 成功**

根因：`v-if` / `v-else` 的两个 `el-table` 是同一组件类型，Vue 复用组件实例，`el-table` 内部列缓存不重建，表头更新而表体仍用旧列。**结论：同一位置切换列结构，必须给组件不同 `key` 强制重建。**
