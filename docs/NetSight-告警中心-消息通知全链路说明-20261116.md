## 0. 一句话结论

NetSight 的消息通知不是“一个发送方法”，而是一条**五入口、两套发送模式、三层主数据、两类模板、十一类通道**的链路：

- **五类消息生成入口**：Webhook 接入、管理端手动发送、用户操作审计、备件低库存、工单派单旁路。
- **两套发送模式**：
  - **自动通知**：事件入库 → 异步规则匹配 → 规则绑定的“消息模板组”决定通道 → 按联系人解析手机号/openid → 发送。
  - **手动通知**：管理员直接选“渠道实例 ID”+联系人 → 同步发送；仍会尝试按事件类型找 `tpl_manual` 等主模板。
- **三层主数据**：`notification_rule`（规则）+ `notification_template`（消息模板/模板组）+ `notify_channel`（渠道实例）。
- **两类模板**：
  - **消息模板**：`notification_template` 表，决定“这条通知写什么、由哪些通道实例发”。
  - **渠道模板**：不是独立表，而是 `notify_channel.config_json` 里第三方平台要求的模板参数（阿里云 `templateCode`、微信 `templateId` 等），决定“第三方平台最终按哪个模板发”。
- **终端消费**：阿里云/腾讯云短信 → 运营商 → 手机短信收件箱；微信公众号 → 微信服务器 → 关注者会话；企业微信/钉钉/飞书/PushPlus/ServerChan/Email/Webhook → 各自终端或系统。
- **回写**：每次通道发送写一条 `notification_log`；事件状态回写 `event_record.status`；同时 WebSocket 广播、页面回显日志条数。

## 4. 主数据：六张表到底存什么

### 4.1 `notification_rule`（通知规则）

关键列：

```text
id, tenant_id, rule_name, event_type, condition_json, receiver_strategy_json,
channels_json, template_id, enabled, create_time, update_time, del_flag
```

- `event_type`：只做**精确相等**匹配，不支持通配。
- `condition_json`：为空 `{}` 表示全匹配；否则逐字段严格字符串相等。
- `receiver_strategy_json`：新格式 `{"type":"fixed","contactIds":[1,2]}`；`parseContactIds` 读 `contactIds`。
- `channels_json`：**历史兼容字段，自动链路不参与发送**。自动链路实际用 `template_id` 决定通道。
- `template_id`：规则绑定的“主模板”，它决定整个模板组。
- `enabled=1` 才参与自动匹配；`listEnabledRules` 按 `id` 倒序，命中多条时只取第一条（最新一条）。

### 4.2 `notification_template`（消息模板 / 模板组）

关键列：

```text
id, tenant_id, template_code, template_name, channel_type, channel_id,
content, enabled, create_time, update_time, del_flag
```

- `template_code`：模板组编码，例如 `tpl_manual`、`tpl_order_dispatch`、`tpl_device_offline`。
- `channel_id`：绑定的渠道实例 ID（`notify_channel.id`）。
- `channel_type`：冗余的类型字段；发送时真正使用的是渠道实例解析出来的 `channelType`。
- `content`：普通通道是文本模板；微信公众号必须是 JSON 描述符。
- 相同 `(tenant_id, template_code, channel_id)` 在服务层做唯一性校验。
- **模板即通道**：规则只绑一个主模板；系统按主模板的 `template_code` 找同租户全部启用模板，同组每条模板绑不同渠道实例，从而实现短信+微信+企业微信等多通道。

### 4.3 `notify_channel`（渠道实例 / 渠道模板参数）

关键列：

```text
id, tenant_id, channel_type, channel_name, config_json, enabled,
health_status, last_check_time, remark, create_time, update_time, del_flag
```

- `channel_type`：11 类之一（见第 10 节）。
- `config_json`：该渠道的全部参数；**“渠道模板”就在这里面**。
- `enabled=0` 的实例在 `resolveChannels` 里直接跳过。
- `config_json` 中的密文字段以 `enc:` 开头；`NotifyChannelService` 负责加解密、掩码。

### 4.4 `notify_contact`（通知联系人）

> 表名是 `notify_contact`，不是 `notification_contact`。这是本项目最容易叫错的表名。

关键列：

```text
id, tenant_id, name, mobile, wechat_openid, wechat_app_id, wechat_bound_at,
remark, status, create_by, create_time, update_by, update_time, del_flag
```

- `mobile`：短信接收地址，也是工单派单旁路按手机号匹配联系人的依据。
- `wechat_openid`：微信公众号 openid；没有 openid 的联系人在微信通道会被过滤。
- `wechat_app_id`：绑定到哪个公众号实例；微信发送时用于 appId 过滤，避免跨公众号串用 openid。
- `wechat_bound_at`：绑定时间。
- `status=1` 才参与发送；`resolveContacts` 会按 `id in + tenant_id + status=1` 查。

### 4.5 `event_record`（事件记录 / 审计同表）

关键列：

```text
id, tenant_id, event_type, event_source, severity, biz_id,
device_name, device_ip, device_type, location,
labels_json, content_vars_json, content, status,
rule_id, rule_name, retry_count, create_time, update_time, del_flag
```

- `event_type`：非空，空则 `PARAM_ERROR`。
- `tenant_id`：空则兜底 1。
- `biz_id`：去重键的一部分；为空则自动链路不去重。
- `labels_json`：既用于 `matchCondition` 取标签字段，也会合并进模板变量。
- `content_vars_json`：AlertManager/标准 Webhook 会写，但当前 `buildVars` **不读它**；模板变量实际来自事件字段 + `labels_json`。
- `status`：`pending → processing → sent/failed/part_failed`。
- `rule_id/rule_name`：命中的规则；无规则或手动发送为 NULL。
- 页面上的 `logCount` 不是表字段，是 `pageEvent` 批量查 `notification_log` 后回填的。

### 4.6 `notification_log`（发送日志）

关键列：

```text
id, tenant_id, event_id, rule_id, rule_name, event_type,
channel_type, channel_id, receivers_json, content, biz_id,
success, error_msg, third_party_msg_id, template_id,
recipient_results_json, cost_time, retry_count,
create_time, update_time, del_flag
```

重点：
- `channel_id`：渠道实例 ID，不是通道类型。
- `template_id`：**来自 `SendResult.templateId`，不是 `notification_template.id`**。微信公众号发送器把它填成第三方微信模板 ID；阿里云/腾讯云发送器不填，所以短信日志该列为 NULL。前端列名叫“微信模板ID”就是这个原因。
- `recipient_results_json`：目前只有微信公众号发送器会写逐接收人结果。
- `content`：普通通道是渲染后的文本；微信是 `WechatTemplatePayload` 的摘要（“模板=xxx；字段=值…”），不是微信最终气泡里的完整 JSON。
- `event_id`：工单派单旁路为 NULL，因为旁路不落 `event_record`。

## 5. 消息生成：五类入口

### 5.1 Webhook 接入

**入口**

```text
POST /alert/push
Header: X-Netsight-Webhook-Token
Header: X-Netsight-Tenant-Id（仅全局 token 过渡模式使用）
Body: AlertManager v4 或标准事件格式
```

**调用链**

```text
AlertPushController.push
  → WebhookTokenService.resolveTenantId(token)
  → AlertPushService.push(body, tenantId)
  → parseToEvents(body, tenantId)
  → 每条 EventRecord 调 EventCenterService.receiveEvent(event)
```

**Token 解析顺序**

1. Redis `netsight:webhook:token:<token>` 命中 → 直接得到 `tenantId`。
2. 未命中 → 全量查 `sys_tenant` 中 `status=1` 的租户，逐个 AES 解密 `webhook_token` 比对。
3. 命中 → 回填 Redis，TTL 24h。
4. 命中租户级 Token 时，**不再信任** `X-Netsight-Tenant-Id`，租户身份由 Token 决定。
5. 未命中租户级 Token，但 Token 等于全局 `netsight.alert.webhook-token` → 回退 `X-Netsight-Tenant-Id`；Header 为空则 tenant 1。
6. 都失败 → 401 `Webhook 接入密钥校验失败`。

**启动硬约束**

`AlertPushController.@PostConstruct validateWebhookToken()`：全局 `WEBHOOK_TOKEN` 为空直接拒绝启动。即使全部使用租户级 Token，全局 token 也不能为空。

**AlertManager v4 映射**

- `labels` / `commonLabels` 取：`severity`、`device_ip`、`device_name`、`device_type`、`device_location`。
- `eventSource=alertmanager`。
- `status=resolved` 时 `severity` 强制 `resolved`。
- `bizId = status + "_" + abs(hash(alertname + deviceIp + generatorURL))`。
- `eventType` 映射：
  - `网络设备离线故障` / `设备离线` → `device_offline`
  - `设备外线状态异常` / `外线异常` / `外线链路异常` → `device_line_abnormal`
  - `故障恢复` / `告警恢复` → `device_recovered`
  - `CPU使用率过高` / `CPU过高` → `device_cpu_high`
  - `内存使用率过高` / `内存过高` → `device_mem_high`
  - 未知 → 保留 `alertname` 原文；空 → `unknown_event`
- `content` 取 `annotations.description` → `annotations.summary` → `alert.summary` → 空串。
- `labelsJson` 存原始 labels；`contentVarsJson` 存 labels+annotations。

**标准事件格式字段**

`event_type`、`event_source`、`severity`、`biz_id`、`content`、`labels`、`content_vars`、`annotations`。

**已知风险（代码推导）**

`bizId` 含 `status`，firing 和 resolved 是不同 key。`device_recovered` 清理的是 `netsight:event:dedup:<bizId>:device_offline`，而 firing 的 key 用的是 firing 的 `bizId`，两者通常不同，所以“恢复后清 firing 去重键”可能不生效。

### 5.2 管理端“事件记录”手动发送

**入口**

```text
POST /alert/event/manual
权限：super_admin 或 alert:event:manual
限流：@RateLimit(key="ip", limit=20, window=60)
审计：@Log(module="告警中心", action="手动发送告警")
Body:
{
  "eventType": "manual_notify",
  "bizId": "...",
  "content": "...",
  "contactIds": [1,2],
  "channels": [9,10]
}
```

**关键语义**

- `channels` 是**渠道实例 ID 列表**（`notify_channel.id`），不是 `"sms"` / `"wechat"` 这样的类型字符串。Controller 注释里的旧示例写成 `"sms","wechat","pushplus"`，实际 `castLongList` 按 Long 解析。
- `channels` 为空 → 400“通知通道不能为空”。
- `contactIds` 为空时，只有所选渠道实例中包含 `pushplus` 才允许；否则 400“请选择通知联系人”。
- `eventType` 默认 `manual_notify`。
- `eventSource=manual`、`severity=info`、`status=pending`。
- `manualEvent` 直接 insert `event_record`，同步 `dispatchManual`；**不经过 `asyncProcess`、不做规则匹配、不做 24h 去重、不发布 `AlertEvent`**。
- Controller 返回 200 时，同步发送已经执行完。

**手动发送的模板行为（容易误解）**

`dispatchManual` 把 `content` 放进 `vars.content`，然后 `channelService.dispatch(event, null, contacts, channels, vars, null)`。`dispatch` 看到 `rule==null` → `dispatchByChannelIds`。

`dispatchByChannelIds` 第一步：

```text
mainTemplate = findManualTemplate(event.tenantId, event.eventType)
```

`findManualTemplate` 按 `MANUAL_TEMPLATE_CODE` 把事件类型映射成模板 code：

| eventType | 模板 code |
|---|---|
| `manual_notify` | `tpl_manual` |
| `stock_low` | `tpl_stock_low` |
| `order_dispatch` | `tpl_order_dispatch` |
| `device_offline` | `tpl_device_offline` |
| `device_line_abnormal` | `tpl_device_line` |
| `device_recovered` | `tpl_device_recovered` |
| `device_cpu_high` | `tpl_device_cpu_high` |
| `device_mem_high` | `tpl_device_mem_high` |

所以：

- 同租户存在 `tpl_manual` 启用模板 → 手动发送会先用该模板内容；
- 再按 `templateCode + channelId + tenantId + enabled=1` 找该通道实例专属模板；
- 找不到专属模板才回落到主模板；主模板也没有，才用 `vars.content`。

这解释了实测中“微信 `template_id` 有值、短信 `template_id` 为 NULL”的差异：微信 sender 会把自己的微信模板 ID 填进 `SendResult.templateId`；阿里云 sender 不填。

**手动发送的假成功**

`dispatchManual`：

```text
failCount = logs.stream().filter(success==0).count()
status = failCount == 0 ? "sent" : (failCount == logs.size() ? "failed" : "part_failed")
```

如果 `logs` 为空（例如跨租户渠道被拦截、渠道禁用、模板组缺失），`failCount=0`，事件会被标记 `sent`，但实际一条都没发。tenant 17 的 7859/7865 就是这个现象。

### 5.5 工单派单旁路

**入口**

**实现要点**

- 按 `template_code=tpl_order_dispatch + tenant_id=order.tenantId + enabled=1 LIMIT 1` 查主模板。
- 构造一个临时 `NotificationRule`，只设 `templateId`。
- 构造内存 `EventRecord`：`eventType=order_dispatch`、`eventSource=workorder`、`severity=warning`、`bizId=orderNo`、`status=pending`、`retryCount=0`。
- 变量含 `orderNo/order_no`、`deviceName/device_name`、`deviceIp/device_ip`、`deviceType/device_type`、`deviceLocation/device_location`、`faultDesc/fault_desc`、`repairerName/repairer_name`、`tenantName/tenant_name`、`content`。

**后果**

- 派单通知不参与自动规则、不参与事件去重；
- 微信发送器仍会按 `bizId=orderNo` 做自己的 24h 去重；
- 工单派单在 feature 分支已能复用联系人 openid，不再“微信必然跳过”（这是相对 master 的修正）。

## 6. 事件入库：`receiveEvent`

### 6.1 方法签名与事务

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public Long receiveEvent(EventRecord event)
```

`REQUIRES_NEW` 的作用：如果从业务事务内调用，事件插入会立即提交，避免“业务事务没提交、异步线程读不到事件”。

### 6.2 处理步骤

1. `tenantId == null` → `1L`。
2. `eventType` 为空 → `PARAM_ERROR`。
3. `status == null` → `pending`。
4. `retryCount == null` → `0`。
5. `eventMapper.insert(event)`。
6. 注册 `TransactionSynchronization.afterCommit()`：
   - 事务提交后，通过 `selfProvider.getObject().asyncProcess(eventId)` 走代理，触发 `@Async("eventExecutor")`。
   - 如果没有同步事务，直接 `dispatch.run()`。

### 6.3 为什么必须 afterCommit

早期实现是在事务内直接调 `asyncProcess`。异步线程 `selectById` 时事务还没提交，读不到事件，直接 return，事件永久停在 `pending`。feature 的 `0656207` 把派发改到提交后，修掉了这个竞态。

### 6.4 入库后的状态

| 状态 | 含义 |
|---|---|
| `pending` | 刚入库，等待异步处理 |
| `processing` | 异步线程已开始处理 |
| `sent` | 已受理/已发送；也可能是无规则、命中去重、空日志假成功 |
| `failed` | 全部通道失败，或异步异常 |
| `part_failed` | 部分通道失败 |

`processing` 是中间态；如果应用在处理中崩溃，可能永久停留，需要人工排查。

## 7. 异步编排：`asyncProcess`

`EventCenterService.asyncProcess(Long eventId)`，`@Async("eventExecutor")`，feature 约 line 146。

### 7.1 完整顺序

1. `eventMapper.selectById(eventId)`；为空直接 return。
2. 发布 `AlertEvent(event)`：
   - `WorkOrderEventListener` 是**同步 `@EventListener`（非 @Async）**；
   - `device_offline` / `device_line_abnormal` → `workOrderService.autoCreateFromEvent(event)`；
   - `device_recovered` → `workOrderService.handleRecover(event)`；
   - 其他不联动；
   - 异常只 `log.error`，不阻断通知。
   - **AlertEvent 在规则匹配之前发布**，所以工单自动建单/归档在通知发送前同步执行。
3. `device_recovered` 且有 `bizId` → 删除 Redis：
   - `netsight:event:dedup:<bizId>:device_offline`
   - `netsight:event:dedup:<bizId>:device_line_abnormal`
4. `status=processing`。
5. `ruleService.listEnabledRules(tenantId)`：
   - `enabled=1`、`tenant_id` 相同、`id` 倒序。
6. 过滤：
   - `event.eventType.equals(rule.eventType)`（精确相等）；
   - `matchCondition(rule, event)`。
7. 无匹配规则 → `markEvent(eventId, "sent", null, null)`，日志“无匹配路由规则，仅记录不发送”，return。
8. 取 `matched.get(0)`，只执行**最新一条**规则。
9. `parseContactIds(rule)` → `resolveContacts(contactIds, event.tenantId)`。
10. `buildVars(event)`。
11. 去重：
    - 仅当 `bizId` 非空；
    - key `netsight:event:dedup:<bizId>:<eventType>`；
    - `setIfAbsent(key, "1", DEDUP_TTL)`；
    - `DEDUP_TTL=24h`；
    - 已存在 → `markEvent(eventId, "sent", rule.id, rule.ruleName)`，跳过发送。
12. `channelService.dispatch(event, rule, contacts, null, vars, null)`。
13. 状态计算：
    - `failCount = logs.filter(success==0).count()`
    - `0` → `sent`
    - 全部失败 → `failed`
    - 部分失败 → `part_failed`
14. `markEvent(eventId, status, rule.id, rule.ruleName)`。
15. `PushWebSocketHandler.broadcast("event", {...})`：
    - `eventId/eventType/severity/deviceName/deviceIp/status/content`
16. 最外层异常 → `markEvent(eventId, "failed")`。

### 7.2 `matchCondition`

`matchCondition(rule, event)`：

- `condition` 为空或 `{}` → 全匹配。
- 否则逐字段：
  - `severity` / `device_type` / `device_ip` / `event_source` 取事件字段；
  - 其他字段取 `labelsJson` 同名 key；
  - 取不到用空串；
  - **字符串严格相等**，没有 `contains`、`>`、`in` 等操作符。

示例：

```json
{"severity":"critical","device_type":"switch"}
```

只匹配 `severity=critical` 且 `device_type=switch` 的事件。

### 7.3 `buildVars`

自动链路变量：

| 变量 | 来源 |
|---|---|
| `device_name` | `event.deviceName` |
| `device_ip` | `event.deviceIp` |
| `device_type` | `event.deviceType` |
| `location` / `device_location` | `event.location` |
| `severity` | `event.severity` |
| `event_type` | `event.eventType` |
| `biz_id` | `event.bizId` |
| `tenant_name` | 按 `tenantId` 查 `sys_tenant.tenant_name` |
| `time` | `event.createTime` 格式 `yyyy-MM-dd HH:mm:ss` |
| 其他 | `labelsJson` 合并，`putIfAbsent` |

关键：**自动链路不显式放 `content`**。所以自动短信模板写 `{{content}}` 会渲染为空；手动链路才有 `vars.content`。微信发送器的 `enrich` 会把 `request.content` 注入 `vars.content`，所以微信描述符可以用 `content`。

### 7.4 为什么“没有规则也是 sent”

`asyncProcess` 无匹配规则时直接 `markEvent("sent")`。这是“已受理但不发送”的语义，不是“已送达”。页面看事件是 `sent`，但发送日志是 0 条。

### 7.5 为什么“命中去重也是 sent”

命中去重时也 `markEvent("sent", rule.id, rule.ruleName)`。事件看起来成功，但这次没有发送。日志文案仍写“5分钟”，实际 24 小时。

### 7.6 工单联动细节

`WorkOrderEventListener` 是同步 `@EventListener`，在 `AlertEvent` 发布时立即执行：

| 事件类型 | 动作 |
|---|---|
| `device_offline` | `workOrderService.autoCreateFromEvent(event)` |
| `device_line_abnormal` | `workOrderService.autoCreateFromEvent(event)` |
| `device_recovered` | `workOrderService.handleRecover(event)` |
| 其他 | 不联动 |

`autoCreateFromEvent` 的关键行为：

1. 按 `event_type + tenant_id + enabled=1` 查规则。
2. 解析接收人 `contactIds`。
3. 取联系人手机号。
4. 按同租户 `repairer.phone` 精确匹配启用维修员。
5. 命中 → 建单即 `status=1` 指派；未命中 → `status=0` 待派单。
6. 24h 去重按 `tenant_id + device_code(=deviceIp) + fault_type + status in (0,1,2) + create_time >= now-24h`。

注意：**自动建单本身不发通知**；只有后续 `WorkOrderService.dispatch` 派单才走 `WorkOrderNotifier` 旁路发送。

## 8. 联系人解析与多租户

### 8.1 `resolveContacts`

`NotificationContactService.resolveContacts(contactIds, tenantId)`：

```text
id in contactIds
+ tenant_id = tenantId
+ status = 1
```

跨租户联系人会被静默过滤为空，不抛业务异常。

### 8.2 `resolveReceiversByChannel`

| 通道类型 | 接收人来源 | 说明 |
|---|---|---|
| `pushplus` | 空列表 | 按租户 token 一对多群发，忽略联系人 |
| `sms` | `mobile` | 去空、去重 |
| `wechat` | `wechat_openid` | 去空、去重；按 appId 过滤：联系人未填 appId 允许，填了且与当前通道 appId 不一致则跳过；未绑定只 warning |
| 其他 | 兜底 `mobile` | `aliyun_sms`、`tencent_sms` 走这个兜底尚可用；`wechat_work`/`email` 等也拿手机号，语义不正确 |

### 8.3 appId 过滤与 `resolveReceiverAppIds`

feature 增加了 `resolveReceiverAppIds(contacts, channelType)`，生成 `openid → appId` 映射，供 sender 标记 `app_id_mismatch`。但 `NotificationChannelService.sendOneResolved/sendOne` 目前**没有把这个映射注入 `SendRequest.extra`**，所以 sender 的 `app_id_mismatch` 标记路径实际可能不生效；联系人侧的 appId 过滤仍然生效。这是代码推导。

### 8.4 微信 openid 绑定链路

> 这一节解释一个常见误解：**手机号登录成功 ≠ openid 自动绑定**。

**入口 A：公众号静默授权（登录前）**

```text
GET /wechat/oauth/start?redirect=/m/login&channelId=...
  → WechatOAuthService.start(redirect, "login", null, channelId, null)
  → 校验 state、mode=login、channelId 对应 notify_channel 且 channelType=wechat
  → 读 appId/appSecret
  → 允许的 redirect 仅 /m/login、/m/orders、/m/order-detail、/m/out-requests、/alert/contact
  → state 写 Redis netsight:wechat:oauth:state:<state>，TTL 10 分钟
  → 生成 https://open.weixin.qq.com/connect/oauth2/authorize?...scope=snsapi_base&state=...#wechat_redirect
```

**回调**

```text
GET /wechat/oauth/callback
  → 校验 state（一次性删除）
  → code 换 openid（https://api.weixin.qq.com/sns/oauth2/access_token）
  → mode=login：生成 ticket 写 Redis netsight:wechat:bind:ticket:<ticket>，TTL 10 分钟
  → 302 回 /m/login?wechatBindTicket=<ticket>
  → mode=bind：直接 bindByContact(contactId, tenantId, openid, appId)，写轮询状态
```

**手机号登录后绑定**

`AuthService.loginByPhone(phone, code, clientType, wechatBindTicket)`：

- 校验短信验证码；
- `clientType=m` 时通过 `RepairerAccountResolver.listBound/listLegacyByPhone` 组合候选，要求“唯一 user+repairer 候选”；多个候选报“手机号关联多个维修人员账号/未关联维修档案”；多个 `SysUser` 报“手机号关联多个账号”；全部禁用报禁用；
- 登录成功后如带 ticket，调 `WechatBindingService.bindByTicket`，绑定结果放 `result.wechatBind`；
- 绑定失败只 warning，不影响登录；无 ticket 返回 `reason=NO_TICKET`。

**`WechatBindingService.bindByTicket` 硬约束**

| 情况 | 结果 |
|---|---|
| 同租户同手机号 0 条联系人 | `CONTACT_NOT_REGISTERED`（提示去告警中心→通知联系人添加并启用，**绝不自动创建**） |
| 全部停用 | `CONTACT_DISABLED` |
| 多条启用 | `CONTACT_AMBIGUOUS`（要求管理员确认唯一联系人） |
| 唯一启用 | `bindToContact` |
| openid 已绑其他联系人 | `OPENID_BOUND_OTHER` |
| 该联系人已绑其他 openid | `CONTACT_BOUND_OTHER` |
| 正常 | 写 `wechat_openid`、`wechat_app_id`、`wechat_bound_at` |

**管理端二维码绑定**

```text
GET /alert/contact/{id}/wechat/bind-url
  权限：super_admin 或 alert:contact:edit
  → start(redirect=/alert/contact, mode=bind, contactId, channelId, tenantId)

GET /alert/contact/wechat/bind-status?ticket=
  权限：super_admin 或 alert:contact:list

POST /alert/contact/{id}/wechat/unbind
  权限：super_admin 或 alert:contact:edit
  @Log(module="通知联系人", action="解绑微信")
```

**代码级缺陷（重要）**

`WechatOAuthController.bindUrl` 的 `channelId` 默认值是硬编码 `7`：

```java
@RequestParam(defaultValue = "7") Long channelId
```

前端 `views/alert/contact/index.vue` 的 `handleBindWechat(row)` 调 `getWechatBindUrl(row.id)` **没有传 channelId**（`api/alert/contact.js` 虽然支持第二个参数，但页面没传）。因此所有租户都默认用渠道实例 7。tenant 17 的微信公众号实例是 10，不是 7；管理员扫码绑定默认走 7，可能查不到或绑到别的租户渠道，这是“管理员扫码绑定后 openid 仍为空”的高概率原因之一。

**“登录了但 openid 还是空”的可能原因清单**

1. 没有从公众号 OAuth 入口进入，登录时没有 `wechatBindTicket`；
2. ticket 过期（10 分钟）；
3. 同手机号没有启用联系人；
4. 同手机号有多条启用联系人 → `CONTACT_AMBIGUOUS`；
5. 联系人已停用；
6. openid 已绑其他联系人；
7. 登录的是非 `m` 端且未传 ticket；
8. 管理端二维码绑定未传 channelId，默认走 7。

是否实际命中，要查 `notify_contact` 对应行 + Redis ticket/绑定状态。

**口径边界：维修人员与通知联系人是两套数据**

截至本文核对的 `feature/wechat-mp-full-support`（`0656207`）源码，`RepairerService` 中没有“创建维修人员时自动创建通知联系人”的联动字段/逻辑。也就是说：

- 创建维修人员 ≠ 自动拥有通知联系人；
- 要让某维修员收到短信/微信，仍需在“通知联系人”里登记并启用对应手机号/openid；
- 如果部署包额外包含了该联动而源码分支没有，以部署包为准，但本文不把它写成 feature 已有行为。

### 8.5 同一手机号有两条维修员记录时，会影响什么

先拆成两个问题：

**问题 A：两条 `repairer` 记录会不会直接让 openid 为空？**

不会。`openid` 是否写入只取决于 `WechatBindingService.bindByTicket` → `bindToContact` 是否拿到有效 ticket、是否找到唯一启用联系人。`repairer` 记录数不参与写 openid。

**问题 B：两条 `repairer` 记录会不会影响登录/绑定链路？**

会影响“能不能走到绑定那一步”。`AuthService.loginByPhone` 的 `m` 端候选解析是：

```text
对每个同手机号启用 SysUser：
  bound = listBound(tenantId, userId)          // user_id 精确匹配，可能多条
  legacy = bound.isEmpty()
      ? listLegacyByPhone(tenantId, phone)     // user_id IS NULL 且非外聘，可能多条
      : []
  candidates = bound + legacy
如果 candidates.size() > 1 → “手机号关联多个维修人员账号，请联系管理员处理”
```

所以：

- 两条都是 `user_id IS NULL` 的存量维修员 → `legacy.size()=2` → `m` 端登录直接报“多个维修人员账号”；
- 一条已绑定 `user_id`、一条 `user_id IS NULL` → `bound` 非空，不再查 legacy → 只取绑定那条，仍可登录；
- 两条都绑定同一个 `user_id` → `bound.size()=2` → 同样报多个；
- 一条启用、一条已离职：`listBound/listLegacyByPhone` 不按 `status` 过滤，仍可能把两条都算进候选，最后由 `assertUsable` 报离职/状态异常。

**因此，“两条维修员记录”更可能造成的是登录候选歧义，不是 openid 为空的直接原因。** 如果用户是在 PC 端或普通手机号登录（没有从公众号 OAuth 入口拿到 ticket），即使只有一条维修员记录，openid 仍为空。

**要定位，按下面四条查：**

```sql
-- 1. 维修员两条记录到底是什么关系
SELECT id, tenant_id, name, phone, user_id, repairer_type, status, del_flag
FROM repairer
WHERE phone = '15669267932' AND del_flag = 0;

-- 2. 通知联系人是否唯一启用
SELECT id, tenant_id, name, mobile, wechat_openid, wechat_app_id, status, del_flag
FROM notify_contact
WHERE mobile = '15669267932' AND del_flag = 0;

-- 3. 同手机号 SysUser 是否唯一启用
SELECT id, tenant_id, username, phone, status, del_flag
FROM sys_user
WHERE phone = '15669267932' AND del_flag = 0;

-- 4. Redis 是否留下过 ticket/绑定状态（在服务器执行）
redis-cli --scan --pattern 'netsight:wechat:bind:ticket:*'
redis-cli --scan --pattern 'netsight:wechat:oauth:state:*'
```

判定顺序：

1. `notify_contact` 是否 0 条启用 / 多条启用 / 已停用；
2. `sys_user` 是否多条启用；
3. `repairer` 两条的 `user_id` 是否为空、是否指向同一 `sys_user`；
4. Redis 是否有 ticket；没有 ticket 就说明登录不是从公众号 OAuth 入口发起的，绑定服务根本没被调用。

## 9. 模板体系：消息模板 vs 渠道模板（重点）

### 9.1 消息模板：`notification_template`

**它是什么**

业务内容模板 + 通道选择器。规则绑定一个主模板，系统按主模板的 `template_code` 找同租户全部启用模板；同组每条模板绑一个 `channel_id`，从而实现多通道。

**示例：一个 `tpl_device_offline` 模板组**

```text
notification_template:
  主模板（短信）: template_code=tpl_device_offline, channel_id=9,  channel_type=aliyun_sms,
                 content="设备{{device_name}}（{{device_ip}}）于{{time}}离线，位置{{location}}"
  同组模板（微信）: template_code=tpl_device_offline, channel_id=10, channel_type=wechat,
                 content='{"templateId":"...","fields":[{"key":"thing2","value":"{{device_name}}","default":"未知设备"}]}'
```

规则只绑“主模板（短信）”。发送时：

```text
mainTemplate = 主模板（短信）
groupTemplates = template_code='tpl_device_offline' + tenant + enabled=1
  → 主模板（短信，channel 9）
  → 同组模板（微信，channel 10）
```

两条都启用且渠道有效时，短信+微信同时下发。

**模板组规则**

- 相同 `(tenant_id, template_code, channel_id)` 唯一（服务层校验）。
- 同组按 `channelType#channelId` 去重；不同实例可以分别发送。
- 模板上的 `channel_type` 是冗余字段；发送时真正使用的是渠道实例解析出的 `channelType`。两者不一致时，实际按渠道实例类型发送。
- `channelId` 当前**必填**；`resolveChannelInstance` 对 `channelId` 为空直接跳过并 warning，**没有按通道类型自动选默认实例的兜底**。
- 代码注释里仍写“未绑则按类型自动选默认”，与实现矛盾；以实现为准。

**微信模板 content 必须是 JSON 描述符**

保存时 `validateWechatContent` 校验：

- 非空；
- ≤ 8KB；
- 合法 JSON；
- `fields` 非空且 ≤ 30；
- `key` 必须匹配 `^[A-Za-z][A-Za-z0-9_]*$`；
- `value` 非空。

示例：

```json
{
  "templateId": "-AItaLZ-5aAGMOxWJ4HHZ5y2AE0rt1DElL8nU0eS8-U",
  "url": "http://www.netsightplus.cn/m/orders",
  "fields": [
    {"key": "thing2", "value": "{{device_name}}", "default": "未知设备"},
    {"key": "phrase9", "value": "{{event_state}}", "default": "告警"},
    {"key": "character_string11", "value": "{{device_no}}", "default": "-"},
    {"key": "thing17", "value": "{{location}}", "default": "未登记位置"},
    {"key": "phrase20", "value": "{{severity_text}}", "default": "一般"}
  ]
}
```

**微信字段截断**

| key 前缀 | 截断长度 |
|---|---|
| `thing` / `const` / `first` / `remark` | 20 字 |
| `phrase` / `letter` / `symbol` | 5 字 |
| `character_string` / `number` | 32 字 |
| `amount` / `date` | 10 字 |
| `time` | 20 字 |
| 其他 | 20 字 |

**微信描述符为空/非 JSON 时的默认 5 字段**

| key | 变量 | 默认值 |
|---|---|---|
| `thing2` | `{{device_name}}` | 未知设备 |
| `phrase9` | `{{event_state}}` | 告警 |
| `character_string11` | `{{device_no}}` | `-` |
| `thing17` | `{{location}}` | 未登记位置 |
| `phrase20` | `{{severity_text}}` | 一般 |

**微信模板 ID 优先级**

```text
content 描述符 templateId
  → 渠道 config.templateId
  → 都空 → 发送失败
```

**微信跳转 URL 优先级**

```text
描述符 url
  → extra.wechatUrl
  → 渠道 config.url
  → 全局默认 http://www.netsightplus.cn/m/orders
```

**`render` 与变量**

- `NotificationTemplateService.render`：`{{var}}` 替换；变量缺失替换空串。
- 自动链路 vars 来自 `buildVars`，不含 `content`；手动链路 vars 含 `content`。
- 因此普通短信模板里写 `{{content}}`，在**自动通知**链路会渲染为空；手动发送才拿得到 `content`。
- 微信 sender 的 `enrich` 额外注入 `event_state`、`event_title`、`severity_text`、`device_no`、`biz_id`、`time`。
- `time` 在微信 sender 里取发送时刻 `LocalDateTime.now()`，不是事件 `createTime`。

### 9.2 渠道模板：`notify_channel.config_json`

**它不是独立表，也不是一个菜单。**

它是渠道实例里、第三方平台要求的模板参数。举例：

**阿里云短信**

```json
{
  "accessKeyId": "...",
  "accessKeySecret": "...",
  "signName": "NetSight",
  "templateCode": "SMS_512061244",
  "templateVarNames": "deviceName,deviceIp,time",
  "endpoint": "dysmsapi.aliyuncs.com",
  "regionId": "cn-hangzhou"
}
```

- `templateCode`：阿里云短信模板 ID。
- `templateVarNames`：该阿里云模板需要哪些变量，逗号分隔，小驼峰。
- `AliyunSmsChannelSender` 不使用 `request.content` 作为短信正文；它用 `templateCode + signName + templateVarNames` 构造阿里云 `TemplateParam`。
- 所以**日志里的 `content` 与用户手机收到的短信正文可能不一致**。

**微信公众号**

```json
{
  "appId": "...",
  "appSecret": "enc:...",
  "templateId": "-AItaLZ-5aAGMOxWJ4HHZ5y2AE0rt1DElL8nU0eS8-U",
  "url": "http://www.netsightplus.cn/m/orders",
  "mockMode": false,
  "rateLimitPerMinute": 4,
  "dedupTtlHours": 24,
  "timeoutMs": 5000,
  "retryIntervals": "1000,2000",
  "oauthPublicBaseUrl": "https://api.netsightplus.cn/prod-api"
}
```

- `templateId`：微信公众号模板 ID。
- `appId/appSecret`：换 `access_token`。
- 发送时按 openid 逐个发。

**腾讯云短信**

```json
{
  "sdkAppId": "...",
  "secretId": "...",
  "secretKey": "...",
  "signName": "...",
  "templateId": "...",
  "region": "ap-guangzhou"
}
```

### 9.3 两类模板的区别

| 维度 | 消息模板 | 渠道模板 |
|---|---|---|
| 存储位置 | `notification_template` 表 | `notify_channel.config_json` |
| 是否有菜单 | 有，“消息模板” | 无独立菜单，在“渠道管理”里配 |
| 决定什么 | 这条通知写什么、字段怎么映射、由哪些通道实例发 | 第三方平台最终按哪个模板、哪些变量发 |
| 典型字段 | `template_code`、`channel_id`、`content` | 阿里云 `templateCode/signName/templateVarNames`；微信 `templateId`；腾讯云 `templateId` |
| 谁绑定它 | 通知规则绑主模板 | 渠道实例自带 |
| 多通道怎么实现 | 同一 `template_code` 多条模板，每条绑不同 `channel_id` | 每个渠道实例各自一份 config |
| 改动影响 | 改内容/加通道，改这里 | 改第三方模板/密钥，改这里 |
| 典型误解 | 以为规则里的 `channels_json` 决定通道 | 以为“渠道模板”是另一张表/另一个菜单 |

**一句话记忆**

> 消息模板决定“**发什么、发给哪些通道**”；渠道模板决定“**第三方平台按哪个模板发**”。

### 9.4 模板与通道的完整关系图

> 下面是一个 `tpl_device_offline` 模板组的示例，`channel_id=9/10` 借用 tenant 17 的渠道实例做示意；不是说 tenant 17 的两条模板 109/110 就是这个编码。

```text
notification_rule
  └─ template_id ──► notification_template（主模板）
                        ├─ template_code = tpl_device_offline
                        ├─ channel_id = 9 ──► notify_channel(id=9)
                        │                       ├─ channel_type = aliyun_sms
                        │                       └─ config_json.templateCode = SMS_512061244  ← 渠道模板
                        └─ 同组同 code 的另一条：
                            channel_id = 10 ──► notify_channel(id=10)
                                                  ├─ channel_type = wechat
                                                  └─ config_json.templateId = -AItaLZ-...  ← 渠道模板
```

## 10. 发送执行层：`NotificationChannelService`

### 10.1 `dispatch` 分支

```java
if (rule != null && rule.getTemplateId() != null) {
    return dispatchByTemplateGroup(...);
}
return dispatchByChannelIds(...);
```

- 自动通知：`rule != null && templateId != null` → 模板组。
- 手动通知：`rule == null` → 渠道实例 ID 列表。
- 工单派单：构造的临时 `rule` 有 `templateId` → 模板组。

### 10.2 `dispatchByTemplateGroup`

feature 约 line 89。

1. 按 `rule.templateId + event.tenantId` 查主模板。
   - 查不到 → warning“规则模板不属于事件租户”，返回空 logs。
2. 按 `mainTemplate.templateCode + tenantId + enabled=1` 查同组模板。
   - 空 → 返回空 logs。
3. 遍历同组模板：
   - `resolveChannelInstance(tpl, tenantId)`：
     - `channelId` 为空 → warning + null；
     - `resolveChannels` 空 → null；
     - 没有类型兜底。
   - `channelType = ch.channelType`。
   - `channelKey = channelType#channelId`，按通道实例去重。
   - `resolveReceiversByChannel(contacts, channelType, appIdOf(ch))`。
   - `sendOneResolved(...)` → 日志 + `doneChannelKeys`。
4. 短信失败降级：
   - `fallbackEnabled && success==0 && (sms || *_sms || *sms) && !done.contains("wechat_work#null")`
   - 在同组找 `wechat_work` 实例；
   - `sendOneResolved(...)`；
   - 日志 + done + break。

**降级注释陷阱**：注释写“降级为公众号”，代码找的是 `wechat_work`（企业微信），不是微信公众号。且 `"wechat_work#null"` 这个 guard 与实际 key `wechat_work#<id>` 不一致，多短信实例时可能重复降级发送。代码推导。

### 10.3 `sendOneResolved`

feature 约 line 164。

1. `channelRegistry.get(channelType)`；未注册 → `buildFailLog`。
2. `rawContent = template.content`。
3. **wechat 类型不渲染**，原样交给 sender 解析描述符。
4. 其他类型 `NotificationTemplateService.render(rawContent, vars)`。
5. 注入 config。
6. 构造 `SendRequest`：
   - `receiverList`
   - `contentVars`
   - `content`
   - `channelId`
   - `bizId`
   - `tenantId`
   - `gatewayCode`（`labelsJson.gateway_code`）
   - `extra`
   - `channelConfig`
7. `sendWithRetry`。
8. 落 `NotificationLog`：
   - `tenantId/eventId/ruleId/ruleName/eventType/channelType/channelId`
   - `receiversJson`
   - `content`
   - `bizId`
   - `success`
   - `errorMsg`
   - `thirdPartyMsgId`
   - `templateId = SendResult.templateId`
   - `costTime`
   - `retryCount`：逐接收人最大 retry 或通道级 retry
   - `recipientResultsJson`：非 null 才写

### 10.4 `dispatchByChannelIds`

feature 约 line 222。

1. `channelIds` 空 → 空 logs。
2. `mainTemplate = findManualTemplate(event.tenantId, event.eventType)`。
3. `resolveChannels(channelIds)`。
4. 按 `channelType#channelId` 去重。
5. `resolveReceiversByChannel`。
6. `sendOne(event, null, mainTemplate, channelType, receivers, vars, extra, ch)`。

### 10.5 `sendOne`

feature 约 line 272。

1. `registry.get`；未注册 → `buildFailLog`。
2. `channelInstanceId`。

### 10.6 `sendWithRetry`

feature 约 line 431。

- `@Value("${netsight.alert.retry-intervals:1000,2000,3000}")`。
- 首次 `send`。
- 失败且 `retryable` 且 `recipientResults == null` 时循环：
  - `Thread.sleep(intervals[retry-1])`；
  - 重发；
  - `retry < intervals.length`。
- 默认 3 个间隔 → **首次发送 + 最多 3 次重试，总发送最多 4 次**；日志 `retry_count` 记录实际重试次数。
- 逐接收人通道（`recipientResults != null`）已在 sender 内部按人重试，通道层不得整批重发。
- 最终失败 `log.error`。
- `fallbackEnabled` 默认 true。

- `errorMsg=通道未注册`；

### 11.2 阿里云短信

**发送链路**

```text
应用 → 阿里云短信 API（dysmsapi.aliyuncs.com）
     → 运营商
     → 用户手机短信收件箱
```

**关键行为**

- `PhoneNumbers`：接收人手机号逗号拼接。
- `SignName`：渠道 config。
- `TemplateCode`：渠道 config。
- `TemplateParam`：由 `templateVarNames` 逐项构造 JSON。

- 取不到的变量传空串。
- 非 OK 返回 fail。
- 成功 `thirdPartyMsgId=body.bizId`。
- `healthCheck` 恒 true。
- **`SendResult` 不带 `templateId`**，所以日志 `template_id=NULL`。

**实测**

- 3446 `third_party_msg_id=563017394816381738^0`。
- 3448 `736710594816413303^0`。
- 3451 `248919994820145880^0`。

**注意**

阿里云 sender 不使用 `request.content` 作为短信正文；日志 `content` 与手机收到的短信正文可能不一致。

### 11.4 微信公众号

**发送链路**

```text
应用 → 微信服务器（api.weixin.qq.com）
     → 关注公众号用户 openid
     → 微信会话中的公众号模板消息
```

**Token**

- `WechatTokenProvider` 管理。
- Redis key `netsight:wechat:token:<appId>`。
- 提前 300s 失效。
- 本地 `ConcurrentHashMap` 兜底。
- `40001/40014/42001` 强制刷新。
- `STABLE_TOKEN_URL=https://api.weixin.qq.com/cgi-bin/stable_token`。

**发送**

- `TEMPLATE_SEND_URL=https://api.weixin.qq.com/cgi-bin/message/template/send`。
- 默认跳转 `http://www.netsightplus.cn/m/orders`。
- `receiverList` 空 → 失败“无有效微信接收人（联系人的 wechat_openid 为空）”。
- mock 开关 `netsight.alert.channel.wechat.mock-mode:false`。
- 超时 5000ms。
- 逐 openid POST；每人最多 `MAX_ATTEMPTS=3`。
- `errcode=0` 成功。
- `40001/40014/42001` 强制刷新 token 重试一次。
- 其他错误码有提示：`40003/40164/43004/45009/45026/47003` 等。

**去重**

```text
key = netsight:notify:dedupe:<tenantId>:<channelId or appId>:<bizId>:<templateId>:<sha256(openid)前8字节>
```

- `manualSend = !StringUtils.hasText(request.getBizId())`。
- 手动发送若 `bizId` 为空 → 绕过 24h 去重。
- 手动发送若填了 `bizId` → `manualSend=false`，仍可能参与去重。
- 非手动发送先 `setIfAbsent` 60s 锁；成功后写 OK TTL `dedupTtlHours`（默认 24h）；失败释放锁。

**频控**

```text
key = netsight:wechat:rate:<appId>:<openid>:<yyyyMMddHHmm>
```

- 默认每人每分钟 4 条。
- 超限 → `skipped rate_limit`。

**appId 不匹配**

- `receiverAppIds` 映射若存在且与当前 appId 不同 → `skipped app_id_mismatch`。
- 但当前通道中心未注入该映射，实际主要靠联系人侧 appId 过滤。

**结果**

- `success` 仅在无失败、无频控、无 appMismatch 且 `successCount==nonDuplicate` 时为 true。
- 若全部 duplicate → 视为成功并提示“全部接收人已发送过，跳过”。
- 逐接收人写 `RecipientResult`：
  - `receiver` 脱敏（前6+`****`+后4）
  - `errcode`
  - `errmsg`
  - `retryCount`
  - `skipped`
  - `skipReason`
- `renderedContent` 是“模板=xxx；字段=值…”摘要，写日志 `content`。
- `thirdPartyMsgId` 是最后一个成功 `msgid`。
- `retryable=false`。
- 微信模板 ID 优先级：描述符 `templateId` → 渠道 `config.templateId`；都空失败。
- 跳转 URL 优先级：描述符 `url` → `extra.wechatUrl` → `config.url` → 全局默认。
- `healthCheck` 要求 `appId/appSecret` 且（`config.templateId` 或 `config.content`）非空。

**实测**

- 3447 `errcode=0`、`third_party_msg_id=4785266769341218820`。
- 3449 `4785267051735318534`。
- 3452 `4785329686568796162`。

- 忽略 `receiverList`，按 token 群发。
- 支持 mock。

### 11.12 Webhook

- 读取 `url/method/headers`，支持 GET/POST。
- 只要 HTTP 调用未抛异常就返回 success，**不校验响应体/业务码**。
- `secret/bodyTemplate` 未使用；`headers` 不在 meta 里，前端无法配置。
- 终端是任意 HTTP 端点，成功判定很宽。

### 11.13 “发送成功”不等于“用户收到”

| 层 | 能证明什么 | 不能证明什么 |
|---|---|---|
| `SendResult.success` | 发送器认为调用成功/第三方返回成功 | 终端一定展示 |
| 阿里云 `thirdPartyMsgId` | 阿里云受理 | 运营商一定送达 |
| 微信 `errcode=0` + `msgid` | 微信服务器受理 | 用户一定点开/看到 |
| PushPlus `code=200` | PushPlus 受理 | 用户一定收到 |
| Webhook `success=true` | HTTP 没抛异常 | 对端业务一定处理 |

## 12. 日志、状态与页面回显

### 12.1 `notification_log` 写入时机

每个通道实例发送一次，写一条日志。不是每个接收人一条；微信的逐接收人结果放在 `recipient_results_json` 里。

### 12.2 事件状态计算

```text
failCount = logs 中 success==0 的数量
0            → sent
全部失败      → failed
部分失败      → part_failed
```

空 logs 时 `failCount=0` → `sent`，这是“假成功”的根源。

### 12.3 事件记录页

- 查询：事件类型/级别/状态。
- 列表：ID/事件类型/级别/设备/设备位置/匹配规则/发送（日志条数）/状态/发生时间/操作。
- 手动发送弹窗：通知内容/接收人（多选联系人）/通知通道（多选渠道实例）。
- 提示：“短信/公众号按所选联系人发送；仅推送(PushPlus)可不选”。
- 事件详情：事件 ID/类型/级别等。
- `pageEvent` 非超管强制 `tenant_id`；未显式传 `eventType` 时排除 `user_operation`；按当前页 eventIds 批量查日志回填 `logCount`。

### 12.4 发送日志页

- 查询：事件类型/通知通道/发送结果。
- 列表：ID/事件 ID/事件类型/匹配规则/通道/微信模板 ID/接收人/发送内容/结果/第三方 ID/耗时/发送时间。
- 展开行：接收人/结果/错误码/错误信息/重试次数/跳过原因。
- 列名“微信模板ID”对所有通道都显示 `templateId` 字段；短信为空是正常的，不是丢数据。

### 12.5 操作日志页

- 查询：关键字。
- 列表：ID/模块/操作内容/来源 IP/请求 URI/状态/操作时间/操作。
- 详情：ID/模块/操作内容/来源 IP/请求 URI/状态/操作时间/扩展信息。
- `pageOperationLog` 只查 `event_type=user_operation`；keyword 匹配 `deviceName/content/location`；非超管强制 tenant。

### 12.6 WebSocket

`PushWebSocketHandler.broadcast("event", {...})` 在状态回写后推送：

- `eventId`

## 14. 多租户设计复盘

### 14.1 租户身份的三种来源

| 场景 | 租户来源 |
|---|---|
| Webhook | 租户级 Token 反查；全局 token 过渡模式用 `X-Netsight-Tenant-Id`，缺省 1 |
| 管理端登录态 | `SecurityUtils.getTenantId()` |
| 异步线程 | 事件自己的 `event.tenantId`，联系人/模板查询显式传入 |
| 登录审计 | 无登录上下文，兜底 1 |
| 工单派单 | `order.tenantId` |

### 14.2 隔离点

- `pageEvent` / `pageOperationLog` 非超管强制 tenant。
- `NotificationRuleService.pageRule` 非超管强制 tenant。
- `NotificationContactService.resolveContacts` 显式 `tenant_id`。
- `NotificationTemplateService` 增改查校验 tenant。
- `NotifyChannelService` 的 `resolveChannels` 没有 tenant 参数，依赖 MyBatis 租户拦截器；跨租户渠道查不到 → 空列表，不抛业务错误。
- `dispatchByTemplateGroup` 主模板必须属于事件租户；不属于则跳过。
- 工单派单按 `order.tenantId` 查模板/联系人。

### 14.3 已实测的隔离问题

| 编号 | 现象 | 影响 |
|---|---|---|
| P0 | tenant 17 手动发送选 tenant 1 的渠道 4 → 事件 7859 `sent`、0 日志 | 实际未发送但状态成功 |
| P0 | tenant 17 手动发送选渠道 4 + 联系人 1 → 事件 7865 `sent`、0 日志 | 同上 |
| P1 | tenant 1 操作日志能看到 tenant 17 管理员手机号 `19900000010` 的 23 条登录审计 | 跨租户审计泄露 |
| P1 | `/alert/channel/list` 阿里云短信 `accessKeyId/accessKeySecret` 明文 | 密钥泄露风险 |
| P2 | 短信日志正文与终端短信正文可能不一致 | 排查误导 |

### 14.4 密钥掩码现状

`SECRET_FIELDS` 当前包含：

```text
token, appSecret, appKey, accessKey, accessSecret, secret,
webhook, password, apiKey, apiSecret, corpSecret
```

**不包含** `accessKeyId/accessKeySecret`、`secretId/secretKey`、`sendKey`。

所以：

- 阿里云 AK/SK 不加密；
- 腾讯云 `secretId/secretKey` 不加密；
- ServerChan `sendKey` 不加密；
- 微信 `appSecret` 加密并显示 `enc:****`。

`encryptConfig` 只对非 `enc:` 开头值加密；`decryptConfig` 只解 `enc:` 开头；`maskConfig` 对非空值掩码（≤4 位 `****`，否则前 4 位 + `****`）。

## 16. 运维排查手册

### 16.1 事件 `sent` 但发送日志 0 条

按顺序查：

1. 是否有匹配规则：`event_type` 精确相等、`enabled=1`、`condition_json` 满足。
2. 规则 `template_id` 是否为空。
3. 主模板是否属于事件租户。
4. 同 `template_code` 是否有启用模板。
5. 每条模板 `channel_id` 是否为空。
6. 渠道实例是否 `enabled=1`，且属于事件租户。
7. 是否命中 24h 去重（`bizId` 非空）。
8. 是否跨租户渠道被拦截（手动发送）。

### 16.2 事件 `failed`

- 查看 `notification_log.error_msg`。
- 短信：阿里云返回码、模板 CODE、签名、变量。
- 微信：`errcode/errmsg`、openid、appId、templateId、token、mock、频控、去重。
- 其他：键名是否匹配 sender 读取键。

### 16.3 事件 `part_failed`

- 至少一个通道成功、至少一个失败。
- 看每个通道的 `success`。
- 常见：短信成功、微信无 openid 失败；或微信成功、短信模板变量为空失败。

### 16.4 微信失败排查

按顺序：

1. `notify_contact.wechat_openid` 是否为空。
2. `wechat_app_id` 是否与当前渠道 `appId` 一致。
3. 渠道 `appId/appSecret` 是否正确。
4. 渠道 `templateId` 或模板描述符 `templateId` 是否为空。
5. 是否 mock 模式。
6. 是否被 24h 去重（同一 `bizId+templateId+openid`）。
7. 是否被频控（每人每分钟 4 条）。
8. 是否 `40001/40014/42001` token 失效。
9. 是否 `45009` 接口频率限制、`43004` 未关注、`40003` openid 无效。

## 19. 术语表

| 术语 | 含义 |
|---|---|
| 事件 | `event_record` 一行；告警/审计/备件/手动都落这里 |
