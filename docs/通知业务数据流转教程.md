# NetSight 通知业务数据流转教程

> 面向后续维护人员。本文基于 `netsight-server` 当前真实源码编写，所有类名、方法名、表名均与代码一致，可对照阅读。
> 包路径根：`com.netsight.modules.alert`（告警中心）、`com.netsight.framework.aspectj`（日志切面）。

---

## 1. 整体分层与设计思想

通知业务采用**三层解耦**，新增业务来源或新增通知通道都不需要改动另外两层：

| 层 | 职责 | 核心类 |
|---|---|---|
| 接入层 | 接收外部告警（AlertManager webhook）、手动发送、业务模块（工单派单）触发 | `AlertPushController` / `AlertEventController` / `WorkOrderService` |
| 事件中心层 | 事件统一入库 → 规则匹配 → 去重 → 路由到通道中心；同时发布 Spring 事件给工单等业务联动 | `EventCenterService` |
| 通道中心层 | 选模板 → 渲染占位符 → 按 channelType 找 SPI 适配器 → 发送 + 重试 + 降级 → 落发送日志 | `NotificationChannelService` / `ChannelRegistry` / 各 `XxxChannelSender` |

一句话概括数据流：

```
AlertManager(边缘网关)
   │  POST /alert/push  (Header: X-Netsight-Webhook-Token)
   ▼
AlertPushController.push()          ← 租户级 Token 反查 tenantId
   ▼
AlertPushService.push()             ← 报文解析成 EventRecord
   ▼
EventCenterService.receiveEvent()   ← 同步入库 event_record，异步触发
   ▼
EventCenterService.asyncProcess()   ← 规则匹配 + Redis 去重 + 路由
   ▼
NotificationChannelService.dispatch() ← 模板渲染 + 逐通道发送
   ▼
ChannelRegistry.get(channelType)    ← SPI 自动发现的适配器
   ▼
XxxChannelSender.send(SendRequest)  ← 调第三方 API（PushPlus/短信/钉钉…）
   ▼
notification_log 落库               ← 每次发送一条日志
```

## 2. 入口一：AlertManager 自动告警（主链路）

### 2.1 `AlertPushController.push()`
文件：`modules/alert/controller/AlertPushController.java`

- 路由：`POST /alert/push`，**免登录**，走 Header 密钥鉴权（不在 Spring Security JWT 白名单之外，由 `SecurityConfig` 放行）。
- 入参：
  - Header `X-Netsight-Webhook-Token`：租户级 Token（V1.1.6 起每个租户一个）。
  - Header `X-Netsight-Tenant-Id`：仅过渡期兼容用。
  - Body：AlertManager v4 原生报文或标准事件 JSON。
- 鉴权顺序（代码里就是这个 if/else 顺序）：
  1. `webhookTokenService.resolveTenantId(token)`：先查 Redis，未命中查 `sys_tenant.webhook_token`（AES 密文，内存 decrypt 比对，**不能用等值 SQL 查密文**，因为 AES-256-GCM 每次加密 IV 不同）。命中 → 事件归属该租户。
  2. 未命中租户 Token，回退全局 `WEBHOOK_TOKEN` 环境变量 + Tenant-Id 头（打 warn 日志，提示迁移）。
  3. 都失败 → 抛 401。
- `@PostConstruct validateWebhookToken()`：生产环境没配 `WEBHOOK_TOKEN` 直接拒绝启动。

### 2.2 `AlertPushService.push(body, tenantId)`
文件：`modules/alert/service/AlertPushService.java`

- `parseToEvents()` 兼容两种报文：
  - **AlertManager v4**：body 含 `alerts[]` 数组，走 `buildFromAlertManager()`，逐条生成事件；公共标签从 `commonLabels` 取。
  - **标准格式**：body 含 `event_type` 字段，走 `buildFromStandard()`。
- `ALERTNAME_MAP`：把中文 alertname 映射成系统内部 event_type：
  - `网络设备离线故障`/`设备离线` → `device_offline`
  - `设备外线状态异常`/`外线异常` → `device_line_abnormal`
  - `故障恢复`/`告警恢复` → `device_recovered`（且 AlertManager `status=resolved` 也直接映射为 `device_recovered`）
- `genBizId(alertname, deviceIp, generatorUrl, status)`：用这三者拼指纹做 `hashCode`，生成去重业务 ID。
- 每个事件调一次 `eventCenterService.receiveEvent(event)`。

### 2.3 `EventCenterService.receiveEvent(event)`
文件：`modules/alert/service/EventCenterService.java`

- `@Transactional(propagation = REQUIRES_NEW)`：**立即提交事务**，保证后面异步线程能读到刚插入的事件行。
- 补默认值：tenantId 空则置 1、status=`pending`、retryCount=0。
- `eventMapper.insert(event)` 落 `event_record` 表。
- 关键：`selfProvider.getObject().asyncProcess(eventId)` —— 通过 `ObjectProvider<EventCenterService>` 拿**自身 Spring 代理**再调异步方法。
  - 为什么不能直接 `this.asyncProcess()`：`@Async` 走 AOP 代理，同类自调用会绕过代理，导致异步方法在调用线程同步执行，webhook 接口会阻塞到通知发完（PushPlus 重试可达 10s+），边缘网关会超时重传。

### 2.4 `asyncProcess(eventId)`（`@Async("eventExecutor")`）
异步线程池 `eventExecutor` 中执行，步骤即源码顺序：

1. **发布 Spring 事件**：`eventPublisher.publishEvent(new AlertEvent(event))`。
   - 用途：解耦业务联动。`WorkOrderService.onAlertEvent(AlertEvent)`（`@EventListener`）监听它——`device_offline`/`device_line_abnormal` 自动建工单，`device_recovered` 自动归档未完成工单。try-catch 包裹，业务联动失败不影响通知主流程。
2. **恢复事件清去重键**：若 `eventType=device_recovered`，删除 Redis 键 `netsight:event:dedup:{bizId}:device_offline` 和 `:device_line_abnormal`，保证"恢复后再离线"能再次通知。
3. 事件状态置 `processing`。
4. **规则匹配**：
   - `ruleService.listEnabledRules(tenantId)` 取租户内启用规则。
   - 过滤 1：`eventType` 必须相等。
   - 过滤 2：`matchCondition(rule, event)` —— condition JSON 为空全匹配；否则按 severity/device_type/device_ip/event_source/labels 字段**等值匹配**。
   - 无匹配 → `markEvent(sent, null, null)`，仅记录不发送。
   - 取 `matched.get(0)`（当前设计一条事件只跑第一条命中规则，改多规则广播需自行扩展）。
5. **解析接收人与通道**：
   - `ruleService.parseContactIds(rule)` → 联系人 ID 列表。
   - `contactService.resolveContacts(contactIds, tenantId)` → 联系人对象列表（**异步线程无登录态，必须显式传 tenantId**，否则跨租户串数据）。
   - `ruleService.parseChannels(rule)` → 渠道实例 ID 列表（notify_channel.id，实例化升级后是 ID 而非字符串类型）。
6. **组装模板变量**：`buildVars(event)` 输出：
   - `device_name / device_ip / device_type / location / device_location / severity / event_type / biz_id / tenant_name / time`
   - `labels_json` 里的标签 `putIfAbsent` 合并进来（不覆盖上面显式字段）。
   - `tenant_name` 由 `resolveTenantName(tenantId)` 查 `sys_tenant` 得到。
7. **Redis 去重**：
   - key = `netsight:event:dedup:{bizId}:{eventType}`，`setIfAbsent`，TTL = `DEDUP_TTL = 24h`。
   - 命中去重 → 标记 sent，跳过发送。
   - **历史坑**：此前是 5 分钟，设备持续离线时 AlertManager 周期性重推相同内容，被 PushPlus 风控 code=999 拒收；改成 24h 后只通知一次。
8. **路由分发**：`channelService.dispatch(event, rule, contacts, channels, vars, null)`，返回每条通道的 `NotificationLog` 列表。
9. **回写事件状态**：统计失败数 → `sent`（全成）/`part_failed`（部分失败）/`failed`（全失败）。
10. **WebSocket 广播**：`PushWebSocketHandler.broadcast("event", {...})` 推大屏/告警中心实时刷新，失败不影响主流程。

## 3. 通道中心：`NotificationChannelService`

文件：`modules/alert/service/NotificationChannelService.java`

### 3.1 `dispatch(event, rule, contacts, channelIds, vars, extra)`

1. **主模板查询**：按 `templateId + tenantId` 查（**异步线程必须显式带 tenantId**，否则 TenantLine 拦截器跳过，会跨租户串用模板）。
2. **解析渠道实例（关键加载环节）**：`notifyChannelService.resolveChannels(channelIds)` —— 这是 `notify_channel` 表数据**唯一**被加载进内存"通道实例"的地方，发送时实时执行（非启动缓存）：
   - 逐个 `channelMapper.selectById(id)` 从 `notify_channel` 表查出整行（channelType / channelName / configJson / enabled / tenantId）；
   - 跳过 `c == null` 或 `enabled == 0` 的实例；
   - `parseConfig(c.getConfigJson())` 把 `config_json`（JSON 字符串）解析成 `Map`；
   - `decryptConfig(cfg)` 把 `SECRET_FIELDS`（token / appSecret / appKey / accessKey / webhook / password / apiKey / corpSecret 等）的 `enc:...` AES-256-GCM 密文解密回明文；
   - 装配成 `Map`：`{channelId, channelType, channelName, config(已解密)}`，返回 List。
   - **注意**：`ChannelRegistry`（SPI）启动时只缓存 `channelType → Sender 类` 的路由，**不含任何租户/实例/密钥数据**；真正的 token 是每次发送由 `resolveChannels` 现查现解密、通过 `SendRequest.channelConfig` 外部传入的。所以一个 channelType 天然可挂多个租户、多个实例（各带各的 token）。
3. **按 channelType 去重遍历**：同一类型只发一次。
4. **按通道解析投递地址**：`contactService.resolveReceiversByChannel(contacts, channelType)`：
   - `sms` → 取联系人 `mobile` 列表
   - `wechat` → 取联系人 `wechatOpenid` 列表（未绑定的记 warn 跳过）
   - `pushplus` → **返回空列表**（PushPlus 用租户 Token 一对多群发，不需要具体接收人）
5. 每个通道调 `sendOne()`。
6. **降级策略**（`netsight.alert.fallback-enabled=true` 默认开）：
   - 若 `sms`/`*_sms` 发送失败，且还没发过 `wechat_work`，自动找租户启用的企业微信渠道实例重发一次。

### 3.2 `sendOne(...)`

1. `channelRegistry.get(channelType)` 取 SPI 适配器；未注册 → `buildFailLog()` 落一条失败日志后返回。
2. `findTemplate(mainTemplate, channelType, channelInstanceId, tenantId)`：**方案 B 两级查找**（`notification_template` 表已加 `channel_id` 列）：
   - **第一级**：按 `templateCode + channelId(具体通道实例) + tenantId + enabled=1` 找绑定到该实例的专属模板；
   - **第二级（兜底）**：第一级没命中（channelId 为空或无专属模板），再按 `templateCode + channelType + tenantId + enabled=1` 找该类型默认模板；
   - 老数据 `channel_id=NULL` 零迁移，自动走第二级兜底，行为与改造前一致。
   - 异步线程无登录态、TenantLine 不生效，两级查询都**显式带 tenantId**，防跨租户串用模板。
3. `NotificationTemplateService.render(rawContent, vars)`：正则 `\{\{\s*(\w+?)\s*\}\}` 做占位符替换。
4. 构造 `SendRequest`（builder 模式）：receiverList / templateId / contentVars / content / bizId / tenantId / gatewayCode（从 labels_json 取 `gateway_code`）/ extra / channelConfig（解密后的渠道配置）。
5. `sendWithRetry(sender, request)`：首次发送，失败按 `netsight.alert.retry-intervals`（默认 1000,2000,3000ms）递增 sleep 后重试，最多重试到间隔数组长度次。
6. **落 notification_log**：tenantId / eventId / ruleId / ruleName / eventType / channelType / receiversJson / content / bizId / success(1/0) / errorMsg / thirdPartyMsgId / costTime / retryCount。

### 3.3 `buildFailLog(...)`
通道未注册等异常兜底也落一条 `success=0` 的日志，保证审计完整。

## 4. SPI 通道适配器机制

### 4.1 接口 `NotificationChannelSender`
文件：`modules/alert/channel/NotificationChannelSender.java`

四个方法：
| 方法 | 作用 |
|---|---|
| `getChannelType()` | 全局唯一标识，如 `pushplus`/`aliyun_sms`/`dingtalk`/`email`，路由靠它 |
| `getChannelName()` | 后台展示名，如 "PushPlus 推送" |
| `send(SendRequest)` | 核心发送逻辑，异常统一包成 `SendResult`，**不向外抛** |
| `healthCheck(Map config)` | 健康检查，渠道管理页每 5 分钟轮询一次 |

### 4.2 `ChannelRegistry`
文件：`modules/alert/channel/ChannelRegistry.java`

- 构造函数注入 `List<NotificationChannelSender>`（Spring 自动收集所有 `@Component` 实现类）。
- 启动时遍历建 `channelType → 实例` 的 Map，打日志 `通知通道已注册: [pushplus] PushPlus 推送`。
- `get(channelType)` 取不到抛 `CHANNEL_NOT_SUPPORT`。
- **新增通道只需**：新建 `XxxChannelSender implements NotificationChannelSender` 加 `@Component`，框架自动发现，核心代码零改动。

### 4.3 现有适配器
`modules/alert/channel/` 下：`AliyunSmsChannelSender`、`TencentSmsChannelSender`、`PushplusChannelSender`、`DingtalkChannelSender`、`WechatWorkChannelSender`、`WechatAppChannelSender`、`FeishuChannelSender`、`ServerChanChannelSender`、`EmailChannelSender`、`WebhookChannelSender`。

### 4.4 示例：`PushplusChannelSender.send()`
文件：`modules/alert/channel/PushplusChannelSender.java`

1. 取 Token：优先 `request.channelConfig.token`（渠道实例配置），没有则 `resolveTenantToken(tenantId, gatewayCode)`：
   - 先按 `gateway_code` 查 `edge_gateway`（网关级 Token，须归属该租户且启用）。
   - 兜底查 `sys_tenant.pushplus_token`（租户级 Token）。
   - DB 里都是 `enc:` 前缀 AES 密文，用 `tokenCrypto.decrypt()` 解密。
2. `mockMode=true` 时只打日志返回成功（开发联调用）；生产 `mock-mode=false`。
3. 真实发送：`HttpUtil.post("https://www.pushplus.plus/send", {token, title, content, template:"html", topic?})`。
4. 返回体 `code==200` 才算成功；`data` 字段作为 `thirdPartyMsgId`。
5. 所有异常 catch 后包成 `SendResult.success(false).errorMsg(...)`，不抛运行时异常。

## 5. 旁路一：管理员手动发送

入口：`AlertEventController.manual()`（`POST /alert/event/manual`，需 `alert:event:manual` 权限，带 `@Log` 注解记录操作日志、`@RateLimit` 限流）。

- 入参：eventType / content / contactIds / channels（**渠道实例 ID 列表**）。
- 校验：channels 不能为空；若没选联系人，所选渠道中必须含 pushplus（pushplus 可空接收人）。
- 调 `EventCenterService.manualEvent(...)`：
  - eventSource=`manual`，severity=`info`，直接 `insert` 事件。
  - 走 `dispatchManual()`：**不走规则匹配、不走 24h 去重**，直接用传入的 contacts+channels 调 `channelService.dispatch()`。
  - 这样管理员补发公告/测试推送不会被去重逻辑吞掉。

## 6. 旁路二：工单派单通知

文件：`modules/workorder/service/WorkOrderService.java`

### 6.1 自动建单：`onAlertEvent(AlertEvent)`
- `@EventListener` 监听事件中心发布的 `AlertEvent`。
- `device_offline`/`device_line_abnormal` → `autoCreateFromEvent()` 自动建联系单（24h 去重）。
- `device_recovered` → `handleRecover()` 把该设备未完成工单置 `5(已自动恢复)`。

### 6.2 手动派单：`dispatch(id, repairerId, remark)`
1. 校验工单状态（仅 `0 待处理` 可派单），更新为 `1 已派单`，加派单时间、派单人，写 `work_order_record`。
2. **通知在事务提交后异步发送**：
   - `TransactionSynchronizationManager.registerSynchronization(...)` 注册 `afterCommit()` 回调。
   - 原因：① HTTP+重试最长数秒，不能占着 DB 事务连接；② 通知失败不回滚派单；③ 事务回滚时不会发出与最终状态不一致的通知。
3. `afterCommit()` 里调 `notifyRepairer(order, repairer)`：
   - 按 `templateCode=tpl_order_dispatch + tenantId` 查派单模板（必须显式带租户）。
   - 构造临时 `NotificationRule` 和 `EventRecord`（eventType=`order_dispatch`，eventSource=`workorder`，bizId=工单号）。
   - 查租户内所有 `enabled=1` 的渠道实例 ID 列表。
   - 调 `channelService.dispatch(...)` 复用通道中心发通知。
4. `pushOrder()` WebSocket 广播工单状态变化。

## 7. 日志体系（三套，别混淆）

### 7.1 业务发送日志：`notification_log` 表

- **谁写**：`NotificationChannelService.sendOne()` 和 `buildFailLog()`，每发一次写一条。
- **谁查**：`NotificationLogService.pageLog()`（`/alert/log` 发送日志页），字段：eventType / channelType / success 过滤，非超管按 tenantId 隔离；`listByEventIds()` 给事件列表批量回显日志数（避免循环查库）。
- **关键字段**：receivers_json（接收人数组 JSON，前端 join 成逗号分隔）、third_party_msg_id（第三方返回的消息 ID，如 PushPlus 的 `6421b719...`）、cost_time（毫秒）、retry_count、error_msg。

### 7.2 事件与操作日志：`event_record` 表（合表设计）

- 告警事件：`event_type=device_offline` 等，由 webhook/手动/派单写入。
- **操作日志**：`OperLogAspect` 切面把人工操作也写成 `event_record`（`event_type=user_operation`）。
  - 文件：`framework/aspectj/OperLogAspect.java`
  - 切点：所有带 `@Log(module="...", action="...")` 注解的 Controller 方法。
  - `@Around` 包裹：执行前后计时，无论成功失败、有无异常，`finally` 里调 `record()` 组装 EventRecord（operator/module/action/method/uri/ip/result/costTime 放 labels_json），调 `eventCenterService.receiveEvent()` 落库。
  - **参数脱敏**：`maskAndTruncate()` 用正则把 password/secret/token/accesstoken/webhookToken/pushplusToken/gatewayToken/smsCode 等字段值替换成 `***`，超长截断 500 字符。
  - IP 取法：X-Real-IP 优先 → X-Forwarded-For **最右段**（Nginx 追加的真实来源在末尾，取首段可伪造）→ RemoteAddr。
  - 切面记录失败 try-catch 兜底，不影响主业务。
- 这样"告警发生→管理员处理→派单→备件领用"全在 event_record 里串成一条审计链。

### 7.3 应用运行日志：logback + `@Slf4j`

- 所有类统一用 Lombok 的 `@Slf4j` 注解，**不写** `private final Logger log = LoggerFactory.getLogger(...)`。
- 配置：Spring Boot 默认 logback，日志文件输出到服务器（`nohup.out` 或 logback-spring.xml 配置的路径）。
- `WebRequestLogAspect`（`framework/aspectj/WebRequestLogAspect.java`）：`@Around("execution(* com.netsight.modules..controller..*(..))")` 记录每个 Controller 请求的 `HTTP method uri ip code 耗时 ms`，只打日志不落库。
- `TraceIdFilter`（`framework/security/`）：每个请求透传或生成 `X-Trace-Id` 放入 MDC，响应头带回；`R.build()` 把 traceId 填进统一返回体，出问题可凭 traceId 串起整次请求日志。

### 7.4 排查问题时怎么找日志

1. **没收到通知**：先查 `notification_log` 表按 event_id 找——看 success=0 时 error_msg 是什么（PushPlus 返回码/超时/未配 Token）。
2. **没产生事件**：查 `event_record` 表按 biz_id/device_ip，看 status（pending/processing/sent/failed）和 rule_id。
3. **异步没执行**：看应用日志里 `事件[xxx]异步处理异常`，以及 `eventExecutor` 线程池是否拒绝。
4. **webhook 没进来**：看 Nginx access.log 和 `AlertPushController` 的 `Webhook 接入密钥校验失败` warn（带来源 IP）。
5. **跨租户串数据**：代码里凡异步线程查 DB 都显式带 `tenantId`（见 `resolveContacts`/`mainTemplate`/`findTemplate`），改代码时务必保持这个模式。

## 8. 关键设计点速查（改代码前必读）

| 点 | 说明 |
|---|---|
| 异步自调用 | 必须 `selfProvider.getObject().asyncProcess()`，不能 `this.asyncProcess()` |
| 异步线程租户上下文 | 异步线程无 SecurityContext，TenantLine 拦截器会跳过；查 DB **必须显式 `.eq(tenantId, event.getTenantId())`** |
| AES 密文不能等值查询 | `enc:` 前缀每次加密 IV 不同，查网关/租户 Token 走全量拉取+内存 decrypt |
| Redis 去重 | key 前缀 `netsight:event:dedup:`，TTL 24h，恢复事件会清键 |
| 失败重试 | `netsight.alert.retry-intervals` 逗号分隔，sendWithRetry 里 Thread.sleep |
| 降级 | sms 失败自动补 wechat_work，开关 `netsight.alert.fallback-enabled` |
| 新通道开发 | 新建 `XxxChannelSender implements NotificationChannelSender` 加 `@Component`，getChannelType 唯一，异常包 SendResult，密钥从 channelConfig 读不硬编码 |
| 通道实例加载 | 唯一在 `NotifyChannelService.resolveChannels()`：发送时按 ID `selectById` → `parseConfig` → `decryptConfig` 解密密钥 → 装配 `{channelId,channelType,channelName,config}`；SPI Registry 只缓存类型→Sender 路由，不存实例/密钥 |
| 模板即通道（方案B） | 通知规则**不再选通道实例**，只选一个主模板（`rule.template_id`）；发送时按主模板的 `template_code` 查该租户下全部启用模板（`dispatchByTemplateGroup`），**同 template_code 下多条模板=多通道**，逐条渲染发送。规则的 `channels_json` 字段废弃不再读取 |
| 模板→通道实例解析 | 遍历组内每条模板 `resolveChannelInstance(tpl, tenantId)`：模板 `channel_id` 非空用 `resolveChannels([id])` 取已配好参数的实例；`channel_id` 为空（存量模板）走 `resolveDefaultByType(channelType, tenantId)` 按类型自动选该租户默认启用实例；都无则跳过。**异步线程必须显式带 tenantId 防跨租户串用** |
| 手动发送 / 派单 | 手动发送走 `dispatchByChannelIds`（前端传通道实例 ID，`findTemplate` 两级兜底）；派单 `notifyRepairer` 构造临时 rule 带 `template_id=tpl_order_dispatch`，自动走模板组驱动 |
| 事务与通知 | 通知一律在 `afterCommit` 发，不占事务连接 |
| 事件状态机 | pending → processing → sent / part_failed / failed |

## 9. ChannelRegistry 与 notify_channel 的关系（易错点）

很多人会混淆这两者，它们是**两个完全不同的维度**：

| 维度 | ChannelRegistry | notify_channel 表 |
|---|---|---|
| 存什么 | **代码实现**：channelType → 哪个 Java 类负责发 | **数据参数**：channelType + 租户 + 解密后的 token/appKey 等 |
| 谁来填充 | Spring 启动时自动收集所有 `XxxSender implements NotificationChannelSender` 的 Bean，按 `getChannelType()` 注册成 map | 管理员在"通道实例"页面手工录入，AES 加密落库 |
| 是否含密钥 | **不含**，只有类路由 | **含**，`config_json` 里的 token 等是 AES 密文 |
| 是否区分租户 | 不区分，全局一份 | 区分，每个租户各自一条实例 |
| 类比 | "快递公司的代码"（顺丰怎么寄、圆通怎么寄） | "你手里的寄件账号"（各自的地址、寄件人信息） |

### 9.1 发送时的两步拼装

发送一条通知，不是"拿到一个加载了参数的 Sender"，而是**代码和参数现场拼装**：

```
模板组遍历一条模板
        │
        ▼
① resolveChannelInstance(tpl, tenantId)        ← 从 notify_channel 表取【参数】
     channelId 非空 → resolveChannels([id])
     channelId 为空 → resolveDefaultByType(type, tenantId)
     结果 = { channelId, channelType, channelName, config(已解密 token) }
        │
        ▼
② channelRegistry.get(channelType)             ← 从 Registry 取【代码实现】
     结果 = PushplusChannelSender 这个类的单例（全局唯一，不含任何租户参数）
        │
        ▼
③ SendRequest.builder().channelConfig(ch.config).build()
     sender.send(request)                        ← 用同一份代码实现 + 当前实例的 token 发出去
```

关键点：**同一个 `PushplusChannelSender` Bean，租户7 和租户2 用不同 token 调的是同一个类**，差别只在第三步塞进 `SendRequest` 的 `config`。

### 9.2 ChannelRegistry 现在的真实使用点

1. `NotificationChannelService.sendOneResolved():153` 和 `sendOne():251` —— **发送主链路**按 channelType 路由到 Sender（核心用途）。
2. `NotifyChannelService.healthCheck():211` —— 每 5 分钟定时健康检查，调 `sender.healthCheck(config)`。

注意：前端"新增通道实例时选渠道类型下拉"用的是 `NotifyChannelService.CHANNEL_META`（一个静态元数据列表，描述每种类型有哪些配置字段），**那不是 ChannelRegistry**。

### 9.3 新增一种通道要动哪两处

- **代码侧**：新建 `XxxSender implements NotificationChannelSender`，加 `@Component`，实现 `getChannelType()`、`send()`、`healthCheck()` —— Spring 自动把它收进 ChannelRegistry，无需改 Registry 本身。
- **数据侧**：管理员在页面新增一条 notify_channel 实例，填该类型的配置字段 —— 即 `CHANNEL_META` 里声明的那些字段。

两者通过 `channelType` 这个字符串 key 关联，互不影响。
