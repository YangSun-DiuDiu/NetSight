# 维修人员档案绑定系统用户账号改造方案

- 版本：v1.0（设计稿，待评审）
- 日期：2026-11-08
- 代码基线：`D:\gitee\gitee\NetSight1.0`，`master`，`62d55fe`
- 范围：运维工单-维修人员页、系统用户管理、H5 维修端登录、移动工单归属、派单校验、数据库字段与权限
- 状态：**只出方案，不改代码、不建表、不部署**
- 结论依据：本轮源码逐文件走查 + `netsight-server/sql` 现有升级脚本；未连接生产库

---

## 0. 结论摘要

**这个逻辑成立，而且有必要做；但必须做成“绑定已有用户账号”，不能做成“选人后复制姓名/手机号再建一份档案”。**

| # | 现状问题 | 根因 | 本方案 |
|---|----------|------|--------|
| 1 | 用户管理里加了人，H5 仍登不上 | 新增维修人员只插 `repairer`，不建 `sys_user`、不分配角色 | 内聘选人绑定；外聘建号 + 建档案，同一事务完成 |
| 2 | 同一名园区员工要在两处各录一次 | 用户管理与维修人员档案是两套主数据，没有关联字段 | `repairer.user_id` 作为唯一关联，姓名/手机号从账号带出 |
| 3 | 用户改手机号后登录断链，或一人出现多条档案 | 登录按手机号匹配，`repairer.phone` 无唯一约束，查询 `LIMIT 1` | 身份主键改为 `user_id`；`(tenant_id,user_id)` 唯一；手机号降级为通知用途 |
| 4 | 休假/离职人员仍可能进 H5 接单 | H5 登录只校验档案存在，不校验 `repairer.status` | 登录与移动端统一校验用户状态、档案状态、租户一致 |

一句话模型：

> `sys_user` 是登录身份，`repairer` 是维修业务档案；`repairer.user_id` 把两者一对一绑定。内聘从用户管理选人绑定，外聘在建维修档案时自动建号，两类人都能登录 H5。

## 1. 现状与源码证据

### 1.1 维修人员数据模型

`netsight-server/src/main/java/com/netsight/modules/workorder/entity/Repairer.java` L14-45：

- 继承 `BaseEntity`：`id / createTime / updateTime / delFlag`
- 业务字段：`tenantId / repairerNo / name / phone / openid / region / deviceTypes / skills / status / remark`
- **没有 `userId`，没有人员类型字段**

`netsight-server/sql/netsight-upgrade-v1.1.4.sql` L12-29：

- `uk_repairer_no (tenant_id, repairer_no)` 是唯一键
- `phone VARCHAR(20) DEFAULT NULL`，**没有唯一约束**
- `status TINYINT NOT NULL DEFAULT 1`：1 在岗 / 0 休假 / 2 离职
- `del_flag` 逻辑删除

结论：当前维修人员档案与系统用户之间没有数据库级关联，只能靠手机号“碰”。

### 1.2 新增维修人员的真实链路

`RepairerService.addRepairer` L67-76：

1. `tenantId = SecurityUtils.getTenantId()`
2. `repairerNo = REP + yyyyMMddHHmmss + 4位随机数`
3. `status` 默认 1
4. **只执行 `repairerMapper.insert(repairer)`**

`RepairerController` L52-57 只接收 `Repairer` 实体，返回新档案 id。

结论：新增维修人员不会创建 `sys_user`，不会分配角色，也不会写任何用户关联。

### 1.3 H5 登录的真实链路

H5 线上入口：`http://www.netsightplus.cn/m/login`。

`AuthService.loginByPhone` L143-192：

1. L145-151：校验并删除 Redis 短信验证码
2. L153-155：按手机号**全局**查 `sys_user`，无租户条件，`LIMIT 1`
3. L159-161：校验 `sys_user.status`
4. L162-171：当 `clientType='m'` 时，按 `Repairer.phone = phone` + `Repairer.tenantId = user.tenantId` 查档案，`LIMIT 1`
5. 档案为空时抛出原文：`当前账号未关联维修人员档案，请联系管理员`
6. L173-191：组装 `LoginUser`，签发 JWT

关键缺口：

- 用户查询是全局 `LIMIT 1`，同手机号多账号时结果不确定
- 档案查询按手机号，不按用户 id
- **不校验 `repairer.status`**
- 不校验档案与用户是否一对一

`MobileWorkOrderController.currentRepairer()` L50-63：

- 用 `SecurityUtils.getLoginUser().getPhone()` + 当前租户查档案
- `LIMIT 1`
- **同样不校验 `repairer.status`**

`/m/order/*` 的 `my-list / my-stats / detail / start / complete / parts` 全部依赖 `currentRepairer()` 返回的 `repairer.id`，再以 `order.repairerId == repairer.id` 判归属。

结论：H5 的身份解析完全建立在手机号上，手机号一变或同号多人，登录和工单归属都会出问题。

### 1.4 用户管理接口边界

`SysUserController` L38-45：

- `GET /system/user/list` 权限为 `hasRole('super_admin') or hasRole('tenant_admin')`
- 只有超管/租户管理员能看用户列表

- 支持 `username / phone / status` 过滤

- 非超管强制本租户

- 用户名全局唯一
- 普通管理员建号归当前租户，超管可指定租户
- 默认密码固定 `admin123`
- 调 `bindRoles` 分配角色

`SysUserService.bindRoles` L190-206：

- **先清空再插入**，不是“追加单个角色”
- 非超管禁止分配 `super_admin`

`SysUserRoleMapper` L28-41：

- 有 `selectRoleIdsByUserId`、`deleteByUserId`、`insertUserRole`
- **没有“追加单个角色”的方法**

结论：维修人员页不能直接复用 `/system/user/list`：

1. 权限不匹配：有 `workorder:repairer:add` 的运维角色未必是 `tenant_admin`
2. 查询不匹配：按姓名搜索不到
3. 返回内容过宽：会把用户管理全量字段暴露给维修人员页

### 1.6 派单链路

`WorkOrderService.dispatch` L393-416：

- 校验工单 `status=0`
- 校验维修员 `status=1`
- 校验 `order.tenantId == repairer.tenantId`
- 落 `repairerId + repairerName 快照 + dispatchTime`

## 2. 业务模型与核心不变式

### 2.1 两类维修人员

| 类型 | 建档入口 | 账号来源 | `repairer_type` | `user_id` | 姓名/手机号 |
|------|----------|----------|------------------|-----------|-------------|
| 园区内部（内聘） | 维修人员页“从用户管理选择” | 已有 `sys_user` | 1 | 必填，绑定选中的用户 | 只读，从账号带出 |
| 外聘（外包） | 维修人员页手工填姓名/手机号 | 保存时自动创建 `sys_user` | 2 | 必填，指向新建账号 | 可编辑；修改时同步账号 |
| 存量未分类 | 历史数据 | 可能已有账号，也可能没有 | 0 | 允许为空 | 保留原值；按需补建/绑定 |

两类人都必须能登录 H5，因此两类人都必须有 `sys_user` 账号。区别只在账号是“已有绑定”还是“随档案自动创建”。

### 2.2 核心不变式

1. **H5 可登录条件**：`sys_user.status=1` 且 `repairer.status=1` 且用户与档案同租户，且档案已绑定该用户；存量未绑定档案走兼容分支，见第 8 节。
2. **新数据强绑定**：新建的内聘/外聘档案，`repairer.user_id` 必填；应用层拒绝空值。
3. **一人一档**：同一租户内 `(tenant_id, user_id)` 唯一；同一手机号不允许再建第二条维修档案。
4. **内聘不覆盖角色**：绑定时只“追加 `repairer` 角色”，不清空用户原有角色。
5. **外聘账号专用**：自动建号只分配 `repairer` 角色，使用随机密码，不沿用 `admin123`。
6. **手机号降级**：手机号只用于短信通知、联系和 H5 验证码登录；新数据的身份关联不再依赖手机号。
7. **跨租户禁止**：用户、档案、工单三者租户必须一致；H5 登录遇到跨租户同号且无法唯一确定时直接拒绝。
8. **类型不可改**：档案创建后 `repairer_type` 不变；要改类型只能删除重建，避免账号生命周期混乱。

### 2.3 已否决方案

| 方案 | 为什么不做 |
|------|------------|
| 选人后复制姓名/手机号，再建一份维修档案 | 用户改手机号后档案变旧值，H5 登录断链；同一人可出现多条档案，工单归属错乱 |
| 外聘只建 `repairer`，不建 `sys_user` | 现有登录链路第一步就查 `sys_user`，会先卡在“手机号或验证码错误”，根本走不到“未关联维修人员档案” |
| 手机号继续作为身份主键，`LIMIT 1` 容忍同号 | 同号多账号时登录结果不确定；跨租户同号会把工单派错人 |
| 直接给 `repairer` 加 `user_id NOT NULL` | 存量档案没有账号，直接加非空约束会导致升级失败或被迫批量造号 |
| 一次性批量回填所有存量数据 | 存量手机号可能重复、缺失或跨租户，批量脚本容易把错误关系固化；本方案改为“兼容 + 按需补建” |

### 2.4 非目标

- 不改 H5 登录页 UI，只改后端解析与错误提示
- 不改 `sys_user` 表结构
- 不做全量存量数据迁移
- 不新增微信 OpenID 绑定逻辑
- 不改普通用户的默认密码策略

## 3. 数据模型改造

### 3.1 DDL

新增升级脚本：`netsight-server/sql/netsight-upgrade-v1.3.1-repairer-user-binding.sql`

```sql
-- NetSight V1.3.1 升级：维修人员档案绑定系统用户账号
-- 执行时间：2026-11-08
-- 说明：只加字段与索引，不做存量数据搬迁

USE netsight;

ALTER TABLE `repairer`
  ADD COLUMN `user_id` BIGINT NULL
    COMMENT '绑定系统用户ID（sys_user.id）' AFTER `repairer_no`,
  ADD COLUMN `repairer_type` TINYINT NOT NULL DEFAULT 0
    COMMENT '人员类型 1内聘 2外聘 0存量未分类' AFTER `user_id`,
  ADD UNIQUE KEY `uk_repairer_user` (`tenant_id`, `user_id`),
  ADD KEY `idx_repairer_phone` (`tenant_id`, `phone`);
```

### 3.2 字段语义

| 字段 | 类型 | 允许空 | 说明 |
|------|------|--------|------|
| `user_id` | BIGINT | 是 | 绑定 `sys_user.id`；新数据必填；存量允许空 |
| `repairer_type` | TINYINT | 否，默认 0 | 1 内聘 / 2 外聘 / 0 存量未分类 |
| `uk_repairer_user` | 唯一索引 | - | 同一租户同一用户只能有一条维修档案 |
| `idx_repairer_phone` | 普通索引 | - | 支撑同租户手机号查询与重复校验，不做唯一约束 |

### 3.3 为什么允许 `user_id` 为空

MySQL 唯一索引对 `NULL` 不去重，`(tenant_id, user_id)` 唯一索引可以同时容纳多条 `user_id IS NULL` 的存量档案：

- 升级不会因为存量档案没有账号而失败
- 存量档案可以继续走手机号兼容登录
- 后续逐条“补建账号/绑定用户”后，`user_id` 被填上，唯一约束自然生效

`repairer_type` 默认 0 而不是 1/2，是为了不猜测存量人员身份。存量记录在列表显示“未分类”，由管理员通过“补建账号/绑定用户”动作完成分类。

### 3.4 实体变更

`Repairer.java` 增加：

```java
/** 绑定系统用户ID */
private Long userId;

/** 人员类型 1内聘 2外聘 0存量未分类 */
private Integer repairerType;
```

同时增加两个非表字段，供列表回显：

```java
@TableField(exist = false)
private String loginUsername;   // 绑定账号的登录名

@TableField(exist = false)
private Integer userStatus;     // 绑定账号状态 1正常 0禁用
```

`sys_user` 表不改结构，继续使用现有 `id / tenant_id / username / password / real_name / phone / status`。

## 4. 接口设计

### 4.1 接口清单

| 方法 | 路径 | 权限 | 作用 |
|------|------|------|------|
| GET | `/workorder/repairer/list` | `workorder:repairer:list` | 分页列表，返回账号回显字段 |
| GET | `/workorder/repairer/options` | `workorder:repairer:list` | 派单下拉，过滤不可接单人员 |
| GET | `/workorder/repairer/user-options` | `workorder:repairer:add` | 内聘选人候选列表 |
| POST | `/workorder/repairer` | `workorder:repairer:add` | 新增维修人员（内聘绑定或外聘建号） |
| POST | `/workorder/repairer/{id}/account` | `workorder:repairer:edit` | 给存量未绑定档案补建/绑定账号 |
| PUT | `/workorder/repairer` | `workorder:repairer:edit` | 修改维修人员 |
| DELETE | `/workorder/repairer/{id}` | `workorder:repairer:remove` | 删除维修人员 |

`/workorder/repairer/user-options` 必须单独实现，不能把 `/system/user/list` 开放给维修人员页。

### 4.2 内聘选人接口

`GET /workorder/repairer/user-options?keyword=&pageNum=1&pageSize=10`

返回：

```json
{
  "total": 23,
  "rows": [
    {
      "id": 22,
      "username": "repairer01",
      "realName": "维修员甲",
      "phone": "19900000002"
    }
  ]
}
```

查询条件：

1. `u.del_flag = 0`
2. `u.status = 1`
3. `u.tenant_id = 当前登录租户`
4. `u.phone IS NOT NULL AND u.phone <> ''`
5. 排除已绑定当前租户维修档案的用户：
   `NOT EXISTS (SELECT 1 FROM repairer rp WHERE rp.tenant_id = u.tenant_id AND rp.user_id = u.id AND rp.del_flag = 0)`
6. 排除 `super_admin` 角色用户：
   `NOT EXISTS (SELECT 1 FROM sys_user_role ur JOIN sys_role r ON r.id = ur.role_id WHERE ur.user_id = u.id AND r.role_key = 'super_admin' AND r.del_flag = 0 AND r.status = 1)`
7. `keyword` 非空时，对 `real_name / phone / username` 做模糊匹配
8. 按 `u.id DESC` 排序

说明：

- 只返回 `id / username / realName / phone`，不返回密码、角色、权限等字段
- 支持分页，避免用户量大时一次性拉全表
- 非超管查询时租户拦截器会自动加租户条件；**代码仍显式带 `tenantId`**，因为超管会绕过租户拦截器

### 4.3 新增维修人员

`POST /workorder/repairer`

```json
{
  "repairerType": 1,
  "userId": 22,
  "name": "",
  "phone": "",
  "region": "1号楼",
  "deviceTypes": "[\"network\",\"camera\"]",
  "skills": "交换机维修,光纤熔接",
```

外聘请求体：

```json
{
  "repairerType": 2,
  "userId": null,
  "name": "张三",
  "phone": "19900000009",
  "region": "2号楼",
  "deviceTypes": "[\"network\"]",
  "skills": "摄像头维护",
  "status": 1,
  "remark": ""

```

```json
{
  "id": 123,
  "loginUsername": "ext_14_ab12cd34",

```

字段规则：

| 字段 | 内聘 | 外聘 |
|------|------|------|
| `repairerType` | 必填 1 | 必填 2 |
| `userId` | 必填 | 必须为空 |
| `name` | 忽略，取 `sys_user.realName` | 必填 |
| `phone` | 忽略，取 `sys_user.phone` | 必填，`^1[3-9]\d{9}$` |
| `region/deviceTypes/skills/status/remark` | 可填 | 可填 |

#### 内聘绑定步骤

事务内按顺序执行：

1. `userId` 非空，否则抛“请选择用户”
2. 按 id 查 `sys_user`；不存在抛“用户不存在”
3. 校验 `user.tenantId == 当前租户`，否则抛“该用户不属于当前租户”
4. 校验 `user.status == 1`，否则抛“该用户已被禁用，请先在用户管理中启用”
5. 校验 `user.phone` 非空且格式合法，否则抛“该用户未维护手机号，无法登录 H5”
6. 校验用户角色不含 `super_admin`，否则抛“超级管理员不能绑定为维修人员”
7. 校验 `(tenant_id, user_id)` 未被其他档案占用，否则抛“该用户已绑定其他维修人员档案”
8. 校验同租户没有其他维修档案使用同一手机号，否则抛“该手机号已存在其他维修人员档案”
9. 插入 `repairer`：
   - `tenantId = 当前租户`
   - `repairerNo = genNo("REP")`
   - `userId = 选中的用户 id`
   - `repairerType = 1`
   - `name = user.realName`
   - `phone = user.phone`
   - 其余取请求值，`status` 默认 1
10. 调 `SysUserService.ensureRole(userId, "repairer")`，**追加**角色，不覆盖原角色
11. 返回 `{ id, loginUsername: user.username, accountCreated: false }`

#### 外聘建号步骤

事务内按顺序执行：

1. `name` 非空，`phone` 非空且格式合法
2. 校验同租户不存在任何 `sys_user` 使用该手机号（含禁用），存在则抛“该手机号已被本租户用户占用，请改用内聘选择”
3. 校验同租户不存在其他维修档案使用该手机号，存在则抛“该手机号已存在其他维修人员档案”
4. 生成登录名：`ext_{tenantId}_{8位随机小写字母数字}`；若已存在则重新生成，最多尝试 5 次
5. 生成随机密码：`UUID` 去横线后取 10 位；BCrypt 加密后写入，**不返回明文**
6. 创建 `sys_user`：
   - `tenantId = 当前租户`
   - `username = 生成的登录名`
   - `realName = name`
   - `phone = phone`
   - `status = 1`
   - `password = BCrypt(随机密码)`
7. 给新账号追加 `repairer` 角色
8. 插入 `repairer`：
   - `userId = 新账号 id`
   - `repairerType = 2`
   - `name / phone` 取请求值
   - 其余取请求值，`status` 默认 1
9. 返回 `{ id, loginUsername, accountCreated: true }`

### 4.4 存量档案补建/绑定账号

`POST /workorder/repairer/{id}/account`

请求体：

```json
{ "repairerType": 1 }
```

规则：

- 仅允许 `user_id IS NULL` 的档案调用；已绑定档案直接抛“该维修人员已绑定账号”
- `repairerType=1`：按档案手机号找同租户、`status=1`、未绑定其他档案的用户；找到则绑定，找不到抛“未找到同手机号用户，请改用外聘建号”
- `repairerType=2`：同租户已有同手机号且未绑定的用户时优先复用；没有则按外聘建号流程创建新账号
- 成功后回填 `user_id` 与 `repairer_type`，返回 `{ id, loginUsername, accountCreated }`
- 该动作只处理单条记录，不做批量迁移

### 4.5 修改维修人员

`PUT /workorder/repairer`

请求体：

```json
{
  "id": 123,
  "region": "1号楼",
  "deviceTypes": "[\"network\"]",
  "skills": "交换机维修",
  "status": 1,
  "remark": ""
}
```

规则：

- `repairerType` 不可修改；请求里带了也忽略
- 内聘：`name / phone` 只读，后端忽略请求中的这两个字段；姓名/手机号以 `sys_user` 为准
- 外聘：`name / phone` 可改
  - 改手机号时，先校验同租户没有其他 `sys_user` 使用新手机号，也没有其他维修档案使用新手机号
  - 校验通过后，同一事务更新 `sys_user.realName / phone` 与 `repairer.name / phone`
- `status` 只改 `repairer.status`，不自动改 `sys_user.status`
- 修改 `sys_user.realName / phone` 后，H5 登录与派单通知立即使用新值

### 4.6 删除维修人员

`DELETE /workorder/repairer/{id}`

规则：

- 内聘（`repairer_type=1`）：只逻辑删除 `repairer`，保留 `sys_user` 与其原有角色
- 外聘（`repairer_type=2`）：逻辑删除 `repairer`；若该账号角色**只有 `repairer`**，同时把 `sys_user.status` 置 0；若账号还有其他角色，保留账号并记录日志
- 存量未分类（`repairer_type=0`）：只逻辑删除 `repairer`，不动账号
- 删除后 H5 登录因找不到有效档案而失败，符合预期

### 4.7 列表与派单选项

`GET /workorder/repairer/list` 增加返回：

## 5. 登录与 H5 链路改造

### 5.1 `loginByPhone` 解析算法

保留验证码校验与一次性删除逻辑，替换 L153-171 的用户/档案查询。

```text
1. 按 phone 查全部 sys_user（不加租户条件，未登录时租户拦截器本来就会跳过）
2. 若为空 -> 抛 PASSWORD_ERROR
3. 若 clientType != 'm'：
   a. 取 status=1 的用户
   b. 0 个 -> 若存在用户则 USER_DISABLED，否则 PASSWORD_ERROR
   c. 多个 -> 抛“手机号关联多个账号，请联系管理员”
   d. 1 个 -> 作为登录用户
4. 若 clientType == 'm'：
   a. 对每个候选用户解析维修档案：
      - 先按 user_id + 该用户 tenant_id 查 repairer
      - 若没有，且该用户对应的档案是存量未绑定，再按 phone + tenant_id + user_id IS NULL 查
   b. 得到 (user, repairer) 候选对
   c. 0 对 -> 抛“当前账号未关联维修人员档案，请联系管理员”
   d. 多对 -> 抛“手机号关联多个维修人员账号，请联系管理员处理”
   e. 1 对 -> 进入状态校验
5. 状态校验：
   a. user.status != 1 -> USER_DISABLED
   b. repairer.status == 0 -> 休假提示
   c. repairer.status == 2 -> 离职提示
   d. repairer.status != 1 -> 通用不可用提示
6. 组装 LoginUser：
   - userId / username / realName / phone / tenantId
   - roles / permissions / isSuperAdmin
   - clientType
   - repairerId（仅 m 端，取解析出的 repairer.id）
7. 签发 JWT
```

要点：

- 不再使用 `LIMIT 1` 直接取第一条
- 同手机号多个用户时，H5 端优先选择“有有效维修档案”的那一个；多个都有档案则拒绝
- 用户状态、档案状态、租户一致性三者都在登录时校验
- 手机号只用于验证码登录，不再决定档案归属

### 5.2 `LoginUser` 与 JWT

`LoginUser` 增加字段：

```java
/** H5 维修端登录时解析出的维修档案ID */
private Long repairerId;
```

`JwtUtils.createToken` 增加 claim：

```java
.claim("repairerId", loginUser.getRepairerId())
```

`JwtAuthenticationFilter.buildLoginUser` 增加恢复：

```java
Long repairerId = claims.get("repairerId", Long.class);
loginUser.setRepairerId(repairerId);
```

原因：

- H5 登录时已经确定了唯一档案，后续每个 `/m/order/*` 请求不必再按手机号重复解析
- 存量兼容档案也能把“登录时选中的那一条”带进 token，避免同一请求内再次按手机号 `LIMIT 1` 选到另一条

### 5.3 `MobileWorkOrderController.currentRepairer()`

改为：

```text
1. 取 LoginUser
2. repairerId = loginUser.repairerId
3. 若 repairerId 为空（升级前签发的旧 token）：
   a. 先按 user_id + tenant_id 查
   b. 查不到再按 phone + tenant_id + user_id IS NULL 查存量
4. 按 id + tenant_id 查 repairer
5. repairer 为空 -> 抛“当前账号未关联维修人员档案，请联系管理员”
6. repairer.status != 1 -> 休假/离职提示
7. 返回 repairer
```

`/m/order/*` 的归属判断继续使用 `order.repairerId == repairer.id`，不需要改业务逻辑。

### 5.4 派单校验

`WorkOrderService.dispatch` 在现有“工单状态、维修员在岗、同租户”校验之后增加：

1. 若 `repairer.userId != null`，查 `sys_user`：
   - 用户不存在 -> 抛“维修人员账号不存在，请重新选择”
   - `user.status != 1` -> 抛“该维修人员账号已被禁用，无法接单”
2. 若 `repairer.repairerType == 2 && repairer.userId == null`：
   - 抛“该外聘维修人员未绑定登录账号，无法 H5 接单，请先补建账号”
3. `repairerType == 0 && userId == null` 的存量档案：
   - 保留原有派单能力，不立即阻断；列表显示“未绑定”，由管理员按需补建

## 7. 权限、安全与审计

| 操作 | 权限 |
|------|------|
| 查看维修人员列表 | `workorder:repairer:list` 或 `super_admin` |
| 查看派单下拉 | `workorder:repairer:list` 或 `super_admin` |
| 查看内聘选人候选 | `workorder:repairer:add` 或 `super_admin` |
| 新增维修人员 | `workorder:repairer:add` 或 `super_admin` |
| 补建/绑定账号 | `workorder:repairer:edit` 或 `super_admin` |
| 修改维修人员 | `workorder:repairer:edit` 或 `super_admin` |
| 删除维修人员 | `workorder:repairer:remove` 或 `super_admin` |

安全约束：

1. **不复用用户管理列表接口**：选人接口只返回必要字段，避免把用户管理数据面暴露给运维角色。
2. **禁止绑定超级管理员**：`super_admin` 不进入候选列表，后端再次拒绝。
3. **禁止跨租户**：用户、档案、工单三者租户必须一致；非超管显式校验，超管也按当前操作租户校验。
4. **随机密码**：外聘账号不使用固定 `admin123`；密码不返回、不落日志。
5. **角色追加**：内聘绑定时只追加 `repairer` 角色，不清空原有角色，避免误删用户权限。
6. **账号与档案联动**：
   - 用户管理修改姓名/手机号时，同步更新已绑定维修档案的 `name/phone`
   - 用户管理删除用户前，若该用户仍绑定有效维修档案，拒绝删除
   - 用户管理更新已绑定用户角色时，确保保留 `repairer` 角色
7. **审计**：新增、补建、绑定、删除都写 `@Log`；外聘建号与删除禁用账号写服务日志。
8. **PII**：选人接口只返回姓名、手机号、登录名；日志不打印密码。

## 8. 存量兼容与数据治理

### 8.1 不做全量迁移

本方案**不批量搬迁存量数据**，原因：

- 存量档案可能没有手机号，可能同手机号多档案，可能跨租户同号
- 批量脚本一旦把错误关系固化，后续排查成本更高
- 用户已明确要求不迁移存量数据

### 8.2 存量档案行为

| 存量情况 | 行为 |
|----------|------|
| `user_id` 为空，同租户同手机号唯一命中一个 `sys_user` | H5 登录兼容放行；列表显示“未绑定账号” |
| `user_id` 为空，同租户同手机号命中多个 `sys_user` | H5 登录拒绝，提示“手机号关联多个维修人员账号” |
| `user_id` 为空，同租户没有匹配用户 | 不能登录 H5；列表显示“未绑定”，提供“补建账号” |
| `user_id` 为空，手机号为空 | 不能登录 H5；列表显示“未绑定”，需先补手机号 |
| `user_id` 已填 | 按新规则走 `user_id` 解析 |

存量兼容分支只用于过渡，新数据不再产生 `user_id` 为空的内聘/外聘档案。

### 8.3 诊断 SQL（只允许在测试库执行）

```sql
-- 各租户未绑定档案数量
SELECT tenant_id, COUNT(*) AS unbound_count
FROM repairer
WHERE del_flag = 0 AND user_id IS NULL
GROUP BY tenant_id;

-- 同租户同手机号多档案
SELECT tenant_id, phone, COUNT(*) AS cnt
FROM repairer
WHERE del_flag = 0 AND phone IS NOT NULL AND phone <> ''
GROUP BY tenant_id, phone
HAVING COUNT(*) > 1;

-- 同手机号多用户（跨租户）
SELECT phone, COUNT(*) AS cnt
FROM sys_user
WHERE del_flag = 0 AND status = 1 AND phone IS NOT NULL AND phone <> ''
GROUP BY phone
HAVING COUNT(*) > 1;

-- 已绑定档案但账号不存在或已禁用
SELECT rp.id, rp.tenant_id, rp.name, rp.phone, rp.user_id
FROM repairer rp
LEFT JOIN sys_user u ON u.id = rp.user_id AND u.del_flag = 0
WHERE rp.del_flag = 0
  AND rp.user_id IS NOT NULL
  AND (u.id IS NULL OR u.status <> 1);
```

生产库 `1.94.26.126:3306/netsight-producton` 严禁用于测试；上述 SQL 只在测试环境 `115.159.194.149` 的 `netsight` 库执行。

### 8.4 后续可选治理

如果后续要把存量档案全部绑定，建议单独做一次性治理脚本，不放进本次功能改造：

## 11. 风险与决策记录

| 风险/决策 | 处理 |
|-----------|------|
| 存量档案没有账号，直接非空会升级失败 | `user_id` 允许 NULL；新数据应用层必填 |
| 存量同手机号多档案 | 不做批量迁移；H5 兼容分支只允许唯一命中，多命中拒绝 |
| 同手机号多用户跨租户 | 登录时按“有有效维修档案”过滤；多个有效档案拒绝 |
| 内聘用户已有其他角色 | 只追加 `repairer`，不清空 |
| 外聘账号密码安全 | 随机密码 + BCrypt，不返回明文；H5 走短信 |
| 用户管理改手机号导致档案旧值 | `SysUserService.updateUser` 同步已绑定档案的姓名/手机号 |
| 用户管理删除已绑定用户 | 拒绝删除，要求先解除维修档案 |
| 删除外聘档案留下可用账号 | 账号只有 `repairer` 角色时同步禁用；有其他角色则保留并记日志 |
| 派单给未绑定外聘 | `type=2` 且 `user_id IS NULL` 直接阻断；`type=0` 存量保留 |
| 旧 token 没有 `repairerId` | `currentRepairer` 先按 userId 查，再按存量手机号兼容 |
| 超管绕过租户拦截器 | 选人、绑定、派单都显式带 `tenantId` 校验 |
